# CPU and Memory Profile

This chapter interprets the V8 CPU profile (`.cpuprofile`) and V8 heap profile (`.heapprofile`) captured by `[../../benchmarks/profile-cpu.sh](../../benchmarks/profile-cpu.sh)` and `[../../benchmarks/profile-heap.sh](../../benchmarks/profile-heap.sh)` respectively. Both captures are taken at the **c=100** concurrency rung sustained for **30 seconds** per the harness defaults documented in [03-load-profile-and-methodology.md](./03-load-profile-and-methodology.md) ("Concurrency Ladder" and "Duration and Warm-up") and codified in `[../../benchmarks/load-profile.json](../../benchmarks/load-profile.json)`'s `c100` scenario (`connections: 100`, `duration: 30`, `warmup: 10`). The diagnostic CLI flags `--cpu-prof` and `--heap-prof` add measurable but bounded overhead to the profiled `node` process per AAP §0.5.4; the numbers reported in this chapter are therefore labeled **"profiled"** and are NOT extrapolated to **"production"** — production-shape numbers (unprofiled, unflagged) are reported in [05-latency-and-throughput.md](./05-latency-and-throughput.md), [06-event-loop-and-concurrency.md](./06-event-loop-and-concurrency.md), and [07-network-latency.md](./07-network-latency.md), which use a vanilla `node ../server.js` launch. The application code path under analysis is the request handler at `[server.js:L6-L10]`; per the per-line walk-through in [01-baseline-characterization.md](./01-baseline-characterization.md) ("Per-Line Walk-Through" and "Hot Path"), only lines 7, 8, and 9 execute per request, and only line 9 (`res.end('Hello, World!\n')`) writes data to the socket. This chapter explains where the captured profiles say CPU cycles are spent and where heap allocations occur — and, equally importantly, where they are **not**, which characterizes the static-handler workload as a minimal-allocation, parser-dominated profile shape.

## Captured Artifacts

The two harness scripts each emit one V8 diagnostic artifact plus one autocannon load summary per run, plus a run manifest and the server's stdout/stderr logs. The artifacts consumed by this chapter are:

- `benchmarks/results/<timestamp>/CPU.<pid>.<id>.<seq>.<thread>.cpuprofile` — V8 CPU samples at 1 ms intervals, emitted by `node --cpu-prof --cpu-prof-dir=<dir> ../server.js` when the process exits cleanly under SIGINT. One file per node main thread per run. The `*.cpuprofile` format is V8's native JSON-encoded sampling profile, consumable by Chrome DevTools and by Speedscope.
- `benchmarks/results/<timestamp>/Heap.<pid>.<id>.<seq>.<thread>.heapprofile` — V8 sampled allocation sites, emitted by `node --heap-prof --heap-prof-dir=<dir> ../server.js` when the process exits cleanly under SIGINT. One file per node main thread per run. The `*.heapprofile` format is V8's native JSON-encoded sampling allocation profile, consumable by Chrome DevTools.
- `benchmarks/results/<timestamp>/autocannon-during-cpuprof.json` — autocannon's machine-readable load summary covering the sustained measurement window during CPU profile capture. Captures the same reporting fields as the baseline run (per chapter 03's "Reporting Fields"): `latency_p50_ms`, `latency_p95_ms`, `latency_p99_ms`, `latency_p99_9_ms`, `rps`, `throughput_bytes_per_sec`, `non_2xx_count`. These numbers are the **profiled** counterparts of the production-shape numbers in chapter 05.
- `benchmarks/results/<timestamp>/autocannon-during-heapprof.json` — autocannon's machine-readable load summary covering the sustained measurement window during heap profile capture. Same field set as the CPU companion.
- `benchmarks/results/<timestamp>/cpu-profile-manifest.json` and `benchmarks/results/<timestamp>/heap-profile-manifest.json` — per-run metadata (timestamp, Node.js version, autocannon version, concurrency, duration, warmup, host fingerprint). The manifest is the authoritative record of what was actually captured; any divergence between the manifest and the discussion below indicates a re-run is needed.
- `benchmarks/results/<timestamp>/server.stdout.log` and `benchmarks/results/<timestamp>/server.stderr.log` — captured stdout and stderr of the profiled `node` process. The first line of `server.stdout.log` should match the startup confirmation emitted at `[server.js:L13]`; any additional lines (warnings about deprecated APIs, V8 internal messages) are inspected before publishing the numbers.

**Inspection conventions.** The `.cpuprofile` file is loaded into Chrome DevTools via the **Performance** tab → "Load profile…" button, or into [Speedscope](https://www.speedscope.app/) via drag-and-drop; both render the V8 sample tree as a flame graph plus a sortable top-down/bottom-up symbol table. The `.heapprofile` file is loaded into Chrome DevTools via the **Memory** tab → "Load profile…" button (selecting the "Allocation sampling" view), which renders the sampled allocation sites as a sortable tree by self-size and total-size. **The `.cpuprofile` and `.heapprofile` artifacts are NOT committed to version control** per AAP §0.8.2 — they are environment-specific (numbers depend on host CPU, kernel, Node.js minor version) and may be many MB in size; only the textual summaries in this chapter are committed.

- **TCP accept and connection setup** — `TCP.onconnection`, the libuv `uv__io_poll` callback dispatch, and the JavaScript-side `Server._handle` paths. For a sustained run at c=100 with keep-alive **on** (the autocannon default per chapter 03's "Request Mix"), these symbols are expected to be lower in the table than parser and write paths because connections are established once per autocannon worker and then reused; for a no-keep-alive variant they would dominate.

**The user handler at `[server.js:L6-L10]` itself.** The anonymous arrow function defined at `[server.js:L6]` should appear in the captured CPU profile — V8 emits it under a label such as `(anonymous)` at `server.js:6` or, after TurboFan optimization, as a compiled frame attributed to the same source location. Its **self-time contribution is expected to be negligible** (well under 1 % of total samples) because the handler does only three things per invocation: assign a status code at `[server.js:L7]`, set one header at `[server.js:L8]`, and call `res.end` with a 14-byte literal at `[server.js:L9]`. None of these operations touches the request body, performs I/O, runs a regular expression, parses JSON, or allocates a non-trivial object — the per-line walk-through in chapter 01 enumerates this exhaustively. The handler is therefore a thin trampoline; the substantive work is performed inside Node.js's `http` module (parser, response object construction) and libuv (socket I/O). **The dominant CPU consumers are in the Node.js runtime layer, not in user code.** This is the expected shape for a minimal static-handler workload and is the canonical reference shape against which any future optimization is compared.

## Flame Graph Interpretation

The flame graph rendered from the captured `.cpuprofile` (in Chrome DevTools' Performance tab or in Speedscope) displays the V8 sample call-tree weighted by sample count: wider boxes represent symbols that appeared in more samples, and vertical stacks represent caller→callee relationships. For the static handler at `[server.js:L6-L10]`, the hot edge of the flame graph typically traces a single path from the libuv event-loop tick down to the socket write, with the user handler as a narrow span midway through the stack. The canonical hot-edge call chain is approximately: `uv_run` (libuv event loop) → `uv__io_poll` (epoll/kqueue/IOCP wait) → `TCP.onread` (libuv-to-JS bridge for the inbound socket) → `HTTPParser.execute` (`llhttp` parser entry) → `parserOnHeadersComplete` (parser-to-JS callback) → `Server._emit` (request emission to the user's `http.createServer` callback) → the anonymous handler at `[server.js:L6-L10]` (status assignment, header set, `res.end` invocation) → `ServerResponse.end` → `Socket._writeGeneric` → `WriteWrap.oncomplete` → `uv_write` (libuv socket write back to the kernel). The handler's portion of the flame is narrow because it executes only three statements per request; the parser entry on the left of the user-handler span and the response/write path on the right of the user-handler span are each substantially wider, reflecting their larger sampled self-time contributions. Operators inspecting the flame graph in Chrome DevTools should toggle between the "Bottom-up" view (which aggregates self-time per leaf symbol, useful for identifying the top-N table above) and the "Call tree" view (which renders the hierarchical flame, useful for confirming the hot-edge chain matches the canonical path above); divergence from the canonical chain — for example, the appearance of a wide GC pause, a deep async-stitching frame, or a userland symbol other than the L6-L10 handler — is reported in the CPU Profile discussion above.

Expected to be roughly co-equal with `IncomingMessage` in total-size.
- **Per-connection `Socket._handle` and TCP wrap objects** — allocated once per accepted TCP connection at the libuv-to-JS boundary. With keep-alive **on**, the per-connection overhead is amortized across many requests per connection; the per-connection allocation site therefore appears in the heap profile but is less concentrated than the per-request `IncomingMessage`/`ServerResponse` sites.
- **Small per-request parser buffers** — `llhttp` reads bytes from the socket into transient buffers; some of these are pool-allocated and reused, but a baseline allocation rate is observable. The sizes are small (typically a few hundred bytes per request at most for the autocannon-default header set per chapter 03's "Request Mix"), so total-size is moderate even at sustained c=100.
- **`Buffer` instances for the response body** — V8 converts the JavaScript string literal `'Hello, World!\n'` at `[server.js:L9]` to a byte buffer for the socket write. Whether this allocates per request or hits a pooled cache depends on the Node.js version's `Buffer` pool policy; the profile will show whether the conversion path allocates fresh memory per call or reuses a pooled allocation. For a 14-byte body well below the `Buffer.poolSize` threshold, pooling is the more likely behaviour, in which case this site has high allocation count but low total-size after the pool fills.

## Retained Memory Across Snapshots

The `--heap-prof` flag emits a single `.heapprofile` per process exit, summarizing the **cumulative** sampled allocations across the full run rather than the **retained** allocations at a specific moment. Identifying retention growth therefore requires either (a) capturing multiple full runs of the harness and comparing the per-run `.heapprofile` files, or (b) supplementing the sampled allocation profile with explicit V8 heap **snapshots** taken at fixed checkpoints during the run via `node --inspect` and the `HeapProfiler.takeHeapSnapshot` inspector method. Option (a) is what the current harness supports out of the box and is the READY harness extension tracked in [09-optimization-recommendations.md](./09-optimization-recommendations.md) as **R9** ("Capture multiple back-to-back heap-profile runs and diff the totals"). Option (b) is the inspector-protocol READY harness extension tracked in [09-optimization-recommendations.md](./09-optimization-recommendations.md) as **R8** ("Sample `process.memoryUsage()` periodically from a harness wrapper"); the same out-of-process inspector-protocol pattern that R8 applies to `process.memoryUsage()` extends to `HeapProfiler.takeHeapSnapshot` for full retention-tree snapshots. Both R8 and R9 live entirely in the `[../../benchmarks/](../../benchmarks/)` harness layer and require zero modification of `[server.js]`, which is why they are tagged READY rather than ADVISORY-C001 — the in-process counterpart (an emission timer inside `[server.js]`) is the separate ADVISORY-C001 entry **A1-6** in chapter 09, surfaced from chapter 11's discussion but kept distinct from the READY harness extensions enumerated here.

**Expected behaviour for the static handler.** For a stateless static-handler workload of the shape at `[server.js:L6-L10]`, the resident set size (RSS) and V8 heap-used totals are expected to **plateau within approximately the first 100 requests** of process startup and remain stable thereafter for the duration of the run. The handler retains nothing between requests — there is no module-level mutable state, no in-memory cache, no connection pool, no session table, no statistics counter that grows over time. Per the per-line walk-through in chapter 01 ("Per-Line Walk-Through"), the only module-level identifiers are `http` (the imported module reference, established once at `[server.js:L1]`), `hostname` (a string literal at `[server.js:L3]`), `port` (a number literal at `[server.js:L4]`), and `server` (the `http.Server` instance constructed once at `[server.js:L6]` and bound at `[server.js:L12]`). None of these grow under load; the `server` instance maintains an internal list of accepted connections, but each entry is reclaimed when its connection closes. **Growth in retained memory beyond the initial plateau would indicate a leak in the Node.js runtime layer or in libuv** — extremely unexpected for this code path, and reportable to upstream maintainers if observed.

## Garbage Collection Pauses

The V8 CPU profile records garbage-collection (GC) activity as named native frames, visible in the captured `.cpuprofile` under labels such as `v8::internal::IncrementalMarking::Step` (incremental marking phase of major GC), `v8::internal::MarkCompactCollector::Sweep*` (major GC compaction passes), `v8::internal::Scavenger::ScavengePage` (minor GC of the young generation), and `v8::internal::Heap::GarbageCollectionPrologue` / `v8::internal::Heap::GarbageCollectionEpilogue` (bookkeeping around GC cycles). These frames are included in the same flame graph as the application-level frames discussed above and contribute to both self-time and total-time percentages in the Top 10 table; operators inspecting the profile can filter to GC-only views in Chrome DevTools by typing `v8::internal::` into the "Filter" box of the Bottom-up view.

For a low-allocation workload of the shape at `[server.js:L6-L10]`, GC pauses are **expected to be infrequent and short**: sub-millisecond minor (scavenge) collections of the young generation triggered by the per-request `IncomingMessage`/`ServerResponse`/parser-buffer allocations described in the Heap Profile section above, and effectively zero major (mark-sweep-compact) collections within the 30-second window because the application retains no long-lived objects beyond the `server` instance itself. The expected GC contribution to total CPU self-time is therefore in the low single-digit percent range or less. If a major GC pause **does** appear prominently in the profile (for example, `v8::internal::MarkCompactCollector` exceeding a few percent of total self-time), that finding is unexpected and requires investigation — most likely root causes would be a V8 internal-tier-up event during the measurement window (mitigated by the 10-second warm-up per chapter 03's "Duration and Warm-up") or an external memory-pressure signal causing V8 to run a major GC defensively.

## RSS Sampling

The V8 CPU and heap profiles record cycles spent and bytes allocated inside the `node` process but do **not** directly report the process's resident set size (RSS) as observed by the operating system. RSS is the kernel-level measure of physical memory backing the process and is the canonical metric for "how much memory is this server using on the host". RSS includes the V8 heap (sampled by the heap profile), the libuv internal bookkeeping (per-connection state, accept queues, write buffers), the native code segments of the `node` binary and any loaded shared libraries, and any anonymous mappings created by the V8 garbage collector. Operators concerned with host-level capacity planning should therefore measure RSS in addition to the V8 heap.

**Sampling approaches.** Three approaches are available to the current harness, in order of increasing fidelity:

1. **Out-of-process sampling via the Node.js inspector protocol** — `process.memoryUsage()` is a Node.js built-in that returns RSS, heap-total, heap-used, external, and array-buffer totals at the moment of the call. The harness can be extended to launch the server with `node --inspect ../server.js`, connect to the inspector socket from a harness-side wrapper, and invoke `process.memoryUsage()` at fixed intervals via the `Runtime.evaluate` inspector method, emitting the readings to a CSV file alongside the existing autocannon JSON output. The inspector socket is a Node.js built-in capability activated by a runtime flag, not an application-source change, so this approach is **READY** and is tracked in [09-optimization-recommendations.md](./09-optimization-recommendations.md) as **R8** ("Sample `process.memoryUsage()` periodically from a harness wrapper"). This is the lowest-overhead in-process sampling approach without requiring source modification; the inspector-protocol invocation is a few microseconds per call and adds no allocations of consequence to the server.
2. **External OS-level sampling via `ps -o rss=` or `pidstat -r`** — POSIX-portable, requires no source modification, and is therefore also **READY**. The harness orchestrator captures the server's PID at launch and can be extended to spawn a `pidstat -r 1` background sampler whose output is collected alongside the V8 artifacts; this is the OS-level sibling of R8 and is tracked in [09-optimization-recommendations.md](./09-optimization-recommendations.md) as **R12** ("Sample RSS and CPU at 1-second cadence during each ladder rung"). The fidelity is one sample per second, which is sufficient for capacity-planning purposes but coarser than the inspector-protocol approach above; R8 and R12 are complementary rather than exclusive — R8 provides V8-internal heap detail unavailable to OS-level tools, while R12 provides OS-visible RSS / CPU% that survives whether or not the inspector connection is active.
3. **Continuous via `cgroup` memory accounting** — when the `node` process runs inside a cgroup (Linux-only), the cgroup's `memory.current` file exposes the same accounting the kernel uses for OOM-killer decisions. This is the most precise approach for production hosts but requires cgroup tooling. It is **READY** at the harness layer (the harness can read `/sys/fs/cgroup/.../memory.current` of the spawned server's cgroup without any source modification to `[server.js]`), but it is contingent on the host configuration providing cgroup-accessible accounting; the current harness does not include it because the loopback-only deployment substrate documented in [03-load-profile-and-methodology.md](./03-load-profile-and-methodology.md) does not place the server inside a controlled cgroup by default. If a future harness extension adds cgroup sampling, the recommendation will be co-listed with R12 under chapter 09's OS-level sampling cluster.

The in-process **emission** counterpart — adding a `setInterval` timer inside `[server.js]` that emits RSS/heap snapshots to stdout from within the process — is a separate **ADVISORY-C001** recommendation tracked in [09-optimization-recommendations.md](./09-optimization-recommendations.md) as **A1-6** ("Add periodic process-telemetry self-report"), with the on-demand SIGUSR2 variant tracked in [11-observability-recommendations.md](./11-observability-recommendations.md) as **O5**. Both A1-6 and O5 require modifying `[server.js]` and are therefore ADVISORY rather than READY; they are kept separate from R8/R9/R12 above precisely so that the harness-side READY extensions (which respect Constraint C-001) are not conflated with the source-modifying ADVISORY entries (which would require lifting C-001 by owner approval). Reviewers selecting which approach to apply should choose R8 first (READY, no constraint relaxation needed) and consider A1-6/O5 only if the inspector-protocol surface is not available in the deployment substrate.

**Expected baseline RSS.** Per the resource requirements table in `[Section "Node.js Version Compatibility"]`, a hello-world Node.js process at idle on a Node.js 20.x runtime is expected to occupy approximately **30–50 MB of RSS**. This is the floor: an idle process holding nothing more than the Node binary, the V8 heap (initially mostly empty), the libuv event loop, and the listening socket. Under sustained load at c=100, RSS is expected to grow by roughly the per-connection libuv bookkeeping cost (~10 KB per accepted TCP connection per chapter 01's "Runtime Baseline Footprint") plus the transient V8 young-generation allocations described in the Heap Profile section above, for a **projected total of 40–80 MB at c=100**, scaling roughly linearly with concurrency above that rung.
