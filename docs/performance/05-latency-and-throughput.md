# Latency and Throughput

This chapter presents the empirical latency and throughput characterization of `[server.js:L1-L14]` produced by `[../../benchmarks/run-baseline.sh](../../benchmarks/run-baseline.sh)` per the methodology codified in [03-load-profile-and-methodology.md](./03-load-profile-and-methodology.md). All numbers in this chapter are sourced from the four `autocannon-{1,10,100,1000}.json` files written to `benchmarks/results/<timestamp>/` by a single invocation of `run-baseline.sh` against a vanilla `node ../server.js` launch — that is, the production-shape baseline, **without** the `--cpu-prof` or `--heap-prof` V8 diagnostic flags whose profiled-shape counterparts appear in [04-cpu-and-memory-profile.md](./04-cpu-and-memory-profile.md). Per AAP §0.6.2, this chapter is the **primary data-presentation chapter** of the report; the executive summary [00-executive-summary.md](./00-executive-summary.md) copies its headline numbers verbatim rather than restating them independently, per AAP §0.6.4 ("Documentation consistency needs"). Where measurements have not yet been captured on the target host, the placeholder `<TBD on first run>` appears — never a fabricated value, per AAP §0.8.1 ("Honesty about absent workflows") and the validation rule in this chapter's agent prompt ("Placeholder pattern").

## Data Sources

The five JSON artifacts consumed by this chapter are written by a single end-to-end invocation of `[../../benchmarks/run-baseline.sh](../../benchmarks/run-baseline.sh)`. All five live under one timestamped directory beneath `benchmarks/results/`:

- `autocannon-1.json` — the c=1 concurrency rung. One TCP connection sustained for the 30-second measured window. Single-connection latency floor; head-of-line blocking on the one connection caps RPS to roughly the reciprocal of the per-request mean latency.
- `autocannon-10.json` — the c=10 rung. Ten parallel TCP connections sustained for 30 seconds. Light interactive load; tail percentiles meaningful through p99.9.
- `autocannon-100.json` — the c=100 rung. One hundred parallel TCP connections sustained for 30 seconds. Mid-tier concurrency at which p99.9 becomes statistically stable per the sample-size rule of thumb in [03-load-profile-and-methodology.md](./03-load-profile-and-methodology.md) ("Sample-Size Targets").
- `autocannon-1000.json` — the c=1000 rung. One thousand parallel TCP connections sustained for 30 seconds. Exercises the TCP listen-backlog (Node.js default 511 per the `http.Server` documentation) and the host's per-process file-descriptor limit; the saturation behaviour observed here is interpreted in [06-event-loop-and-concurrency.md](./06-event-loop-and-concurrency.md) and [07-network-latency.md](./07-network-latency.md).
- `run-manifest.json` — environmental metadata for the run: POSIX epoch-seconds timestamp (the same string that names the surrounding `benchmarks/results/<epoch>/` directory — e.g., `"1779296685"` — captured at launch by `run-baseline.sh:L90`'s `TIMESTAMP=$(date +%s)` and used for both the directory name and the manifest field; the analogous `event-loop-lag-manifest.json` produced by `[../../benchmarks/measure-event-loop-lag.sh](../../benchmarks/measure-event-loop-lag.sh)` uses UTC ISO-8601 form `YYYYMMDDTHHMMSSZ` instead, and the canonical schema-format reference for both flavours is [03-load-profile-and-methodology.md](./03-load-profile-and-methodology.md) "Environmental Recording"), Node.js version (e.g., `v20.20.2` per the setup log — the system Node satisfies `benchmarks/package.json`'s `engines.node` constraint of `>=20.0.0` recorded at `[../../benchmarks/package.json](../../benchmarks/package.json)`), platform `uname -srm`, `ulimit -n` (the soft FD limit reported by the shell at run time; recorded verbatim, including the string `"unlimited"` when the shell reports an unbounded limit), the **autocannon version** that was actually invoked (the `^8.0.0` constraint at `[../../benchmarks/package.json](../../benchmarks/package.json)`'s `devDependencies.autocannon` resolves to a specific 8.x at install time and is recorded verbatim here — read non-mutatingly from the installed package metadata at manifest write time), the list of scenarios that ran, and the list of output filenames. The autocannon-version field is the load-bearing field for this chapter: different autocannon major versions emit slightly different JSON field names and slightly different default header sets, so any reader cross-referencing the raw `autocannon-<N>.json` files against the tables below must first read the manifest to learn which version's schema applies.

All five files are produced by a single invocation of `run-baseline.sh` and share one `<timestamp>` directory under `benchmarks/results/`. Comparing numbers across timestamps is meaningful only when the host environment is identical along the dimensions that the comparison cares about — Node.js minor version for tier-up-related comparisons, kernel release for backlog-related comparisons, autocannon version for header-set-related comparisons, `ulimit -n` for high-concurrency-related comparisons (per [03-load-profile-and-methodology.md](./03-load-profile-and-methodology.md), "Environmental Recording"). The manifest is the canonical evidence file consulted whenever the tables below are compared against a future re-run.

**Interpretation (populate from measurements).** The qualitative shape expected at each rung, against which the measured numbers should be compared, is the following. At **c=1**, latency is dominated by the loopback transport plus per-request handler dispatch — that is, the kernel-side TCP round-trip on `127.0.0.1` per `[server.js:L3]` plus the three statements inside the handler at `[server.js:L7-L9]` (status assignment, header set, body write). On modern Linux, loopback RTT alone is typically sub-100 µs, so the c=1 p50 latency is expected to be a small number of hundreds of microseconds (i.e., sub-millisecond) when rendered to two decimal places of a millisecond; a materially higher measured value would indicate non-trivial handler-side work — surprising given that lines 7-9 contain no I/O, no regex, no JSON parse, no allocation of consequence beyond the per-request `IncomingMessage`/`ServerResponse` documented in [04-cpu-and-memory-profile.md](./04-cpu-and-memory-profile.md) ("Heap Profile"). At **c=10**, latency typically remains close to the c=1 floor because concurrency is not yet saturating any resource — ten parallel connections interleave on the single-threaded event loop without queueing meaningfully. At **c=100**, the p99 / p50 ratio typically begins to spread as the event loop's per-tick budget becomes contended; the p50 may rise modestly while the p99.9 stretches more steeply. At **c=1000**, the latency tail expands sharply if the event loop or the TCP listen-backlog (default 511 per the `http.Server` documentation, discussed in [07-network-latency.md](./07-network-latency.md)) saturates; some connections may queue at the kernel-level accept queue and exhibit latency dominated by accept-time rather than by handler-time. If the c=1000 measured tail does **not** expand — which is possible on hosts with many cores, fast network stacks, and generous `net.core.somaxconn` per [07-network-latency.md](./07-network-latency.md) — the chapter records that fact and the implementing agent extends the ladder per recommendation R3 (chapter 09) to find the actual saturation point.

## RPS Curve and Saturation

The RPS curve typically rises **near-linearly** with concurrency up to an event-loop saturation point and then plateaus or declines as queueing dominates. For the static handler at `[server.js:L6-L10]` running on the single-threaded JavaScript event loop per `[Section 5.2.1]`, the saturation point is expected to be at or above c=100 on typical hardware: the handler executes only three statements per request (status assignment at `[server.js:L7]`, header set at `[server.js:L8]`, body write at `[server.js:L9]`), all of which complete synchronously inside one event-loop tick, so the event loop can dispatch a large number of such ticks per second before contention becomes measurable. The saturation point may not appear at c=1000 at all on hosts with many cores, a fast network stack, and a generous `net.core.somaxconn` (default behaviour discussed in [07-network-latency.md](./07-network-latency.md)) — newer or faster hardware may simply not saturate within the four-rung ladder. If the measured curve continues to rise monotonically through c=1000, the implementing agent should extend the ladder per recommendation **R3 (chapter 09)** with super-high rungs (e.g., c=2000, c=5000, c=10000 — the canonical post-saturation extension values defined in R3) and re-run, recording the extended results in a follow-on subdirectory under `benchmarks/results/` so that this chapter's table can be updated with a true saturation point.

**Saturation criterion.** This chapter adopts a single explicit criterion: **saturation is identified as the concurrency at which RPS plateaus (i.e., the next-higher rung's RPS is within ±5 % of the previous rung's RPS) OR at which p99 latency more than doubles relative to the next-lower rung.** Both halves of the criterion are reported alongside the saturation determination: a plateau alone with stable tail latency would indicate a true throughput ceiling, while a sharp p99 doubling with continued RPS growth would indicate a tail-latency knee that warrants attention even if raw throughput is still rising. The criterion deliberately does not specify *which* rung the saturation occurs at — that is the empirical question the data answers.

## Comparison Against the Implicit SLA

`[Section 4.7.3]` defines three implicit SLA dimensions for this application; each is reproduced verbatim below alongside its measurement approach and a measured-vs-target verdict cell:

- **Startup**: ≤ 1 second from process spawn to readiness.
- **Response determinism**: 100% — every response identical to every other.
- **Throughput**: unspecified — no numeric throughput SLA is imposed by `[Section 4.7.3]`.

**Measurement approach — startup.** Startup time is defined as the wall-clock elapsed time between the `node ../server.js` process spawn (`SERVER_PID=$!` capture in the harness lifecycle per [03-load-profile-and-methodology.md](./03-load-profile-and-methodology.md), "Server Lifecycle") and the first successful HTTP response from the readiness curl-poll. Per the harness lifecycle, the orchestrator polls `curl -fsS --max-time 1 http://127.0.0.1:3000/` at 200 ms intervals for up to 50 attempts (10-second total budget); the **time-to-ready** is the gap between the spawn timestamp and the first 2xx response, and the measurement resolution is therefore ±200 ms (the poll cadence). The current `run-baseline.sh` invocation lifecycle does not yet emit a dedicated `startup_time_ms` field to the manifest, so the measured cell below is populated either (a) by inspecting the harness's runtime logs to compute the gap manually, or (b) by extending `run-baseline.sh` to record the gap explicitly into `run-manifest.json` — the latter is a READY recommendation tracked alongside this chapter's other harness-extension items. Typical loopback startup of a Node.js 20.x process binding `127.0.0.1:3000` per `[server.js:L3-L4]` and `[server.js:L12]` is well under 200 ms on modern Linux, comfortably within the 1-second SLA; until the explicit startup-time field exists, the measured cell records `<TBD on first run — recommend harness extension>` to distinguish "not measured" from "measured zero".

**Measurement approach — response determinism.** Every `autocannon-<N>.json` file records the `non_2xx_count` field (canonical per `meta.reporting_fields`) and autocannon's combined timeouts + socket errors. If both are zero across all four rungs, the determinism SLA is met empirically. The static handler at `[server.js:L6-L10]` always writes the same status (200 at `[server.js:L7]`), the same header set (`Content-Type: text/plain` at `[server.js:L8]`), and the same body (the 14-byte `'Hello, World!\n'` at `[server.js:L9]`) on every request — per `[Section 5.1.3]`, "No data from the incoming request — method, path, headers, or body — is read, evaluated, or stored," so there is no input-dependent branch that could produce a divergent response. Non-2xx counts should therefore be exactly zero at c=1, c=10, and c=100. At c=1000, the TCP listen-backlog (Node.js default 511 per [07-network-latency.md](./07-network-latency.md)) may overflow and cause connection refusals; whether autocannon counts those refusals as `non_2xx_count` or as `errors` depends on the autocannon version recorded in the manifest, and the implementing agent records both observations in the table below.
