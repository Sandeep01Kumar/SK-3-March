# Scalability Assessment

The application's scaling posture is determined by three structural facts: (1) Node.js's single-threaded JavaScript execution model per `[Section 5.2.1]`, which fixes the ceiling on per-process throughput to whatever one core can drive through the event loop; (2) the hardcoded loopback binding at `[server.js:L3]` (`const hostname = '127.0.0.1'`), which makes the server unreachable from any host other than the one it runs on and is documented as ADR-003 per `[Section 6.5.7]`; and (3) the hardcoded port at `[server.js:L4]` (`const port = 3000`), which together with the hardcoded host prevents a second `node server.js` invocation on the same host per Assumption A-002 (`[Section 2.6.1]`) and the scalability discussion in `[Section 2.4.3]`. This chapter quantifies each ceiling, identifies the empirical signals that confirm where the application reaches saturation in its current single-process configuration, and enumerates the four horizontal-scaling options that exist in principle — all four of which require lifting one or more of Constraints C-001 through C-004 per `[Section 2.6.2]` and are therefore tagged **ADVISORY** rather than READY. Per AAP §0.8.1, no horizontal-scaling change can be applied without prior owner approval to lift the corresponding constraint; the only scaling-adjacent items tagged READY in this report are host-level OS/kernel tunables and harness-side measurement extensions, both of which live in [09-optimization-recommendations.md](./09-optimization-recommendations.md) ("READY Recommendations") and are out of scope for this chapter.

## Vertical Scaling (Within One Process)

The application runs as a **single Node.js process**. Per `[Section 5.2.1]`, that process executes all JavaScript on a single thread — the event loop — and delegates only I/O system calls to the libuv thread pool (default size 4, bounded by `UV_THREADPOOL_SIZE`). For the static handler at `[server.js:L6-L10]`, the libuv thread pool is effectively unused because the handler performs no filesystem, DNS, or crypto operations — every byte of work happens on the main thread, dispatched from a single `http.createServer` callback per inbound request. The practical RPS ceiling of one process is therefore determined by the single core's ability to dispatch that callback, run the three statements at `[server.js:L7-L9]` (status assignment at `[server.js:L7]`, header set at `[server.js:L8]`, body write at `[server.js:L9]`), and emit the 14-byte response across the loopback socket. The measured saturation point of this configuration is recorded in [05-latency-and-throughput.md](./05-latency-and-throughput.md) ("RPS Curve and Saturation"); per-rung event-loop lag and probe RTT confirming that the bottleneck is event-loop-bound rather than network-bound are recorded in [06-event-loop-and-concurrency.md](./06-event-loop-and-concurrency.md) ("Per-Rung Lag and Probe RTT").

Vertical scaling within one process is bounded by three distinct factors that compose multiplicatively rather than additively, and the practical ceiling is the minimum of the three rather than their sum:

- **Event-loop per-iteration cost.** Every inbound request is dispatched as one event-loop callback, executes the three lines of the handler at `[server.js:L7-L9]` synchronously, and yields back to the loop after `res.end(...)` returns control. The per-iteration cost is the sum of `http` parser execution, the three handler statements, the V8 string-to-buffer conversion of the literal `'Hello, World!\n'` from `[server.js:L9]`, and the `Socket._write` enqueue. Per [04-cpu-and-memory-profile.md](./04-cpu-and-memory-profile.md) ("CPU Profile" and "Expected dominant symbols"), the dominant on-CPU symbols at saturation are expected to be the Node.js `http` parser entry points (`llhttp_execute` and its JavaScript wrappers) and the socket-write paths (`Socket._write`, `WriteWrap.oncomplete`, libuv's `uv_write`). The implementing agent should confirm the expectation from the captured `*.cpuprofile` once `[../../benchmarks/profile-cpu.sh](../../benchmarks/profile-cpu.sh)` has been executed; until then, the expected shape is the working hypothesis and the chapter's recommendation set assumes it.
- **Response-write throughput from one core.** Even if the parser were free, the kernel-side `write(2)` syscall throughput on a single TCP socket is bounded by the per-core memory-copy bandwidth and the kernel's TCP send-buffer flushing cadence. For 14-byte responses with HTTP/1.1 keep-alive (autocannon's default per [03-load-profile-and-methodology.md](./03-load-profile-and-methodology.md) "Request Mix"), this ceiling is rarely the binding constraint on modern hardware — the loopback transport can sustain millions of small writes per second per core — but it becomes relevant if connection re-use degrades and the kernel begins to incur per-connection setup cost on every request.
- **Kernel TCP stack throughput per accepted connection.** The kernel must complete the three-way handshake for each new TCP connection, allocate socket-buffer memory, and route the accepted file descriptor to the application via the listen-accept queue. Per `[server.js:L12]`'s call to `server.listen(port, hostname, callback)` — invoked without an explicit `backlog` argument — Node.js defaults the accept queue to **511** entries per the `http.Server` documentation, with the kernel-side ceiling further bounded by `net.core.somaxconn`. The detailed treatment of these layers is in [07-network-latency.md](./07-network-latency.md) ("TCP Listen-Backlog and `net.core.somaxconn`"); the relevant point for vertical scaling is that the in-process event loop cannot accept new connections faster than the kernel can drain the SYN queue and post fds to the accept queue, so the kernel queues become the binding constraint before the JavaScript handler does on connection-establishment-heavy workloads.

The interaction of the three factors is captured empirically in the four-rung ladder defined in `[../../benchmarks/load-profile.json](../../benchmarks/load-profile.json)`: at c=1 and c=10 the event loop has ample headroom, at c=100 the per-iteration cost typically begins to bind, and at c=1000 either the event-loop budget or the listen-backlog binds — whichever is tighter on the target host. The chapter's recommendation set treats the event-loop-per-iteration-cost factor as the most actionable lever, because the kernel-side factors are not amenable to in-process optimization without lifting Constraint C-001 anyway. Even with all of the above, the absolute ceiling of one Node.js process is the throughput **one core** can sustain — multi-core utilization is structurally impossible inside one process and is the gating concern that motivates every horizontal-scaling option in the "Horizontal Scaling Options" section below.

## Single-Instance Constraint

The bind address of the listening socket is composed at runtime by `server.listen(port, hostname, callback)` at `[server.js:L12]` from the two constants declared earlier in the file: `hostname = '127.0.0.1'` at `[server.js:L3]` and `port = 3000` at `[server.js:L4]`. Both are literal string and number values respectively; neither is read from an environment variable, a configuration file, or a command-line argument — the absence of such parameterization is itself a deliberate posture codified as Constraint C-004 ("Hardcoded configuration") per `[Section 2.6.2]`. Because both ends of the bind tuple are fixed at compile time, a second invocation of `node server.js` on the same host attempts to bind to the **identical** `127.0.0.1:3000` tuple and is rejected by the operating system's port-binding rules with an `EADDRINUSE` error emitted by the underlying `bind(2)` syscall. The Node.js runtime surfaces this error on the `server`'s `'error'` event and — because `[server.js:L12]` does not register an error handler — the unhandled error causes the second `node` process to exit with a non-zero status, printing a stack trace to stderr. This behaviour is recorded explicitly as Assumption A-002 per `[Section 2.6.1]` ("Single-instance assumption") and as a scalability consideration per `[Section 2.4.3]` ("Horizontal scaling not supported").

`[Section 2.4.3]` states that horizontal scaling is not supported by the current configuration; the structural reason is exactly the one above. **Horizontal scaling on the same host — by which is meant running multiple `node` processes in parallel to absorb load across multiple cores — is structurally impossible without lifting Constraint C-004 to parameterize the port.** Even the lowest-effort multi-process pattern (manually running `node server.js` three times) cannot work, because the second and third invocations fail at `server.listen`. Note that the cluster module discussed in H1 below does **not** suffer this restriction, because all workers spawned by `cluster.fork()` share a single listening socket created by the master process — but adopting the cluster pattern requires modifying `[server.js:L1-L14]`, which lifts Constraint C-001, and introducing a primary/worker process role, which lifts Constraint C-003 ("Single-purpose") at the process-model layer.

The single-instance behaviour is empirically verifiable by the implementing agent without any harness machinery. The verification procedure is:

1. Run `node server.js &` in one shell. The startup log at `[server.js:L13]` confirms the first instance has bound the port: `Server running at http://127.0.0.1:3000/`.
2. In the same shell (or another shell on the same host), run `node server.js &` a second time.
3. The second invocation exits immediately with an unhandled `EADDRINUSE` error and a stack trace pointing to `server.listen` per `[server.js:L12]`. The first instance is unaffected and continues to serve.

The harness's port pre-flight check in `[../../benchmarks/run-baseline.sh](../../benchmarks/run-baseline.sh)` ("Port pre-flight") detects this condition before launching the server: if `127.0.0.1:3000` is already in use by a prior `node server.js` (or any other process), the harness aborts with a clear operator message rather than letting the launch fail mid-benchmark. This pre-flight is intentionally **non-mutating** — it does not kill the prior process, because doing so would risk interfering with a session the operator wants to preserve; instead, the operator is asked to clear the port manually before re-running. The pre-flight is the same logic an operator would apply visually: `ss -lntp | grep ':3000'` or `lsof -iTCP:3000 -sTCP:LISTEN` will reveal the prior holder of the port, and a `kill -INT <pid>` against that PID restores the single-instance invariant.

## Loopback Binding Constraint

The hostname constant at `[server.js:L3]` is the literal string `'127.0.0.1'` — the IPv4 loopback address — and is passed to `server.listen(port, hostname, callback)` at `[server.js:L12]` as the bind address. Binding to `127.0.0.1` makes the server reachable **only** from the same host on which it runs, because the loopback interface is by definition not exposed on any external network adapter. The architectural decision to bind to loopback rather than to `0.0.0.0` (all interfaces) is recorded as ADR-003 per `[Section 6.5.7]` and is one of the load-bearing security postures of the application: by binding to loopback, the application has zero external attack surface — no inbound packet from outside the host can ever reach `[server.js:L6-L10]`. The decision is deliberate, not accidental; recommendations that lift it must explicitly acknowledge the security implication, which is why **H4** below (multi-host distributed deployment) carries ADVISORY-C001 + ADVISORY-C003 + ADVISORY-C004 tags rather than being presented as a trivial "just change the string" change.

For scaling, the loopback binding has two non-obvious implications that compound the single-instance constraint discussed in the previous section:

- **Distributed load testing is structurally impossible.** Per AAP §0.8.1 ("Measurement isolation"), the only host that can drive load against the server is the same host on which the server runs, because no other host has a route to `127.0.0.1` on this host's loopback interface. All measurement chapters in this report — chapters 04, 05, 06, and 07 — drive their load from the same host as the server-under-test. This means the harness shares CPU, kernel scheduler attention, and the loopback transport itself with the server-under-test, which is a known measurement methodology trade-off acknowledged in [03-load-profile-and-methodology.md](./03-load-profile-and-methodology.md) ("Host Isolation"). Eliminating this trade-off would require lifting ADR-003 (binding to a non-loopback interface) and lifting Constraint C-004 (parameterizing the bind so the change can be deployed without modifying source); this is the configuration **H4** below documents.
- **Even with process-level horizontal scaling, external clients cannot reach the server without a proxy.** Suppose the H1 cluster pattern (below) were adopted on the same host — four worker processes sharing one listening socket on `127.0.0.1:3000`. External clients on the same network as the host **still** cannot reach the server, because the listening socket is bound to the loopback interface and the host's IP stack does not route external packets to loopback addresses by design. Reaching the server from outside the host requires either (a) lifting the loopback binding (the **H4** path), or (b) deploying a separate proxy process — bound to `0.0.0.0` or to a non-loopback interface — that accepts external traffic and forwards it to `127.0.0.1:3000` over the same host's loopback. Option (b) does not modify `[server.js]` and is therefore not subject to Constraint C-001, but it is also not a scaling option per se — it is an exposure option that enables the existing single-instance server to be reached from outside the host without changing its scaling posture. Operators evaluating it should consult the same advisory tagging in chapter 09 because the proxy itself is infrastructure not committed to this repository.

The loopback binding is **not** a defect, a stub, or a pre-production placeholder — it is the central architectural decision of ADR-003 and is the reason this codebase is safe to ship with zero authentication per `[Section 6.4]` ("Security Architecture") and zero input validation per `[Section 5.1.3]` ("Data flow: linear, unconditional, no request data read"). Any recommendation that proposes to lift it implicitly trades safety-by-isolation for reachability; the chapter's recommendation set ensures that trade is made transparent rather than buried in a "just change `127.0.0.1` to `0.0.0.0`" instruction.

## Horizontal Scaling Options

Every option in this section requires lifting at least one of Constraints C-001 through C-004 per `[Section 2.6.2]`, and therefore every option carries an **ADVISORY** tag rather than READY. Per AAP §0.8.1 ("Tagged recommendations") and the validation rule restated in this chapter's agent prompt ("No READY claims"), **no horizontal-scaling option in this chapter is tagged READY** — the only READY scaling-adjacent items in this report are host-level OS/kernel tunables (`net.core.somaxconn`, file-descriptor `ulimit`, `tcp_max_syn_backlog`) and harness-side measurement extensions (extended ladder rungs, longer measurement windows), both of which live in [09-optimization-recommendations.md](./09-optimization-recommendations.md) ("READY Recommendations"). The four options below — **H1** (single-host cluster), **H2** (single-host reverse proxy + multiple instances), **H3** (single-host multi-process orchestration via PM2), and **H4** (multi-host distributed deployment) — are the canonical set of horizontal-scaling levers for a Node.js HTTP application; each lists the proposal, the source-and-dependency footprint, the constraint(s) it would require lifting, the expected effect on throughput, and the corresponding entry in chapter 09 where applicable. (Worker-threads — the `worker_threads` module — is documented in the "Single-Process Multi-Thread Alternative" sub-section below the H-series rather than promoted as an H-numbered scaling recommendation, because its expected lift on the static-handler workload of `[server.js:L6-L10]` is marginal at best and chapter 09 does not promote it as a recommended scaling path for this specific codebase.)

### H1. Cluster module (single-host, multi-process)

- **Tag: ADVISORY-C001 + ADVISORY-C003.**
- **Proposal.** Wrap `[server.js:L1-L14]` in a `cluster` master/worker pattern using the Node.js built-in `cluster` module (`require('cluster')`). The master process forks one worker per logical CPU core (`os.cpus().length`); each worker invokes the existing `server.listen(port, hostname)` call at `[server.js:L12]` against the **same** `port`/`hostname` tuple, and the cluster module — by virtue of its master-arbitrated socket-sharing semantics — distributes inbound connections across workers round-robin (or via the OS-level `SO_REUSEPORT` mechanism on Linux kernels that support it) without producing `EADDRINUSE` errors. The cluster module is responsible for resolving the single-instance constraint that the bare `node server.js` invocation cannot resolve.
- **Footprint.** Approximately 15 source lines added to `[server.js]` — a `cluster.isPrimary` branch that forks workers in the master and a `cluster.isWorker` branch that runs the existing `http.createServer(...).listen(...)` logic in each worker. **No dependency change is required**, because `cluster` is a Node.js built-in (`require('cluster')`), shipped as part of the Node.js standard library — the same posture as `[server.js:L1]`'s `require('http')`. Constraint C-002 ("Zero external dependencies") is therefore **not** implicated by this proposal; Constraint C-001 ("Do not touch source files") **is** implicated because the change is necessarily a source modification; and Constraint C-003 ("Single-purpose") **is** implicated because the process model is expanded from "one process serves all requests" to "one primary forks N workers that each serve requests" — the same primary/worker structural change that O2's URL routing and A3-1's `/health` branch raise in their respective directions. Reasonable reviewers can disagree about whether the cluster expansion counts as a "purpose" change strictly construed, but per the AAP §0.7 codification of C-003 ("Single-purpose"), any change that introduces a new top-level process role — here, the primary's fork-and-supervise loop — is a C-003-relaxation candidate, and the tag is recorded accordingly to keep the constraint inventory honest.
- **Effect.** Throughput is expected to scale **near-linearly with logical CPU core count** for a static-handler workload of the shape at `[server.js:L6-L10]`, because the handler is CPU-bound (handler dispatch + parser + write enqueue) and trivially parallelizable across cores — no shared mutable state exists in `[server.js:L1-L14]` to serialize. Expected lift on a 4-core host is approximately 3x–4x in RPS at the c=100 and c=1000 rungs measured in [05-latency-and-throughput.md](./05-latency-and-throughput.md); the slight sub-linear factor accounts for OS scheduling overhead and the master process's connection-distribution work. On hosts with many cores, the marginal benefit per added core decreases as the loopback transport itself becomes the binding constraint — this is the same kernel-TCP-throughput factor enumerated in "Vertical Scaling" above.
- **Cross-reference.** [09-optimization-recommendations.md](./09-optimization-recommendations.md) **A1-3** ("Cluster module multi-core utilization"). Reviewers approving the lift of Constraints C-001 and C-003 to apply H1 should consult A1-3 for the full constraint-relaxation rationale and any additional sub-recommendations (e.g., graceful worker restart, master-side health checks) that accompany the cluster pattern.

### H2. Multiple instances behind a reverse proxy (single-host, multi-port)

- **Tag: ADVISORY-C001 + ADVISORY-C003 + ADVISORY-C004.**
- **Proposal.** Lift Constraint C-004 to parameterize the port at `[server.js:L4]` — for example, by reading `process.env.PORT` with a fallback to the current literal `3000` — and run multiple `node server.js` processes on distinct ports (e.g., 3001, 3002, 3003, 3004 for a 4-process configuration). Deploy a reverse proxy (nginx, HAProxy, Envoy, or Caddy) bound to `0.0.0.0:80` or `0.0.0.0:443`; the proxy distributes traffic across the upstream `node` processes via its built-in upstream-balancing logic. The reverse-proxy configuration is **not** committed to this repository because it is infrastructure rather than application code; recommendation A4-1 in chapter 09 enumerates the minimal proxy configuration sketch.
- **Footprint.** A single source line at `[server.js:L4]` changes from `const port = 3000;` to (e.g.) `const port = parseInt(process.env.PORT, 10) || 3000;` — the source modification is **C-001**, and the introduction of an environment-variable read is **C-004**. In addition, the deployment topology shifts from "one Node.js process serves all requests" to "a reverse proxy plus N Node.js processes serve requests" — the proxy is a new top-level architectural component that mediates every request before it reaches a `node` process, which is a structural scope expansion captured by **C-003** ("Single-purpose") even though the per-process handler at `[server.js:L6-L10]` is byte-identical to today's single-process posture. The reverse-proxy itself is an external infrastructure component with its own configuration file; running multiple `node` processes requires an external process supervisor (systemd, PM2, supervisord) or shell-level job control. No application-package dependency is added, so Constraint **C-002 is NOT implicated** by H2 itself; if the operator chooses PM2 specifically as the multi-process supervisor (per H3 below), that choice introduces C-002 separately and is tracked in H3.
- **Effect.** Similar to H1 in raw throughput lift (~3x–4x on a 4-process configuration on a 4-core host), but with a more complex deployment topology. The reverse proxy adds one extra hop per request — typically sub-millisecond on the same host but non-zero — and introduces a single point of failure that the cluster pattern (H1) does not. H2 is preferred over H1 when: (a) the operator wants in-place rolling restarts where individual processes can be replaced without affecting the listening socket; (b) different upstream processes might serve different code versions during canary deployment; (c) the proxy is already deployed for TLS termination, request routing, or rate limiting. For the static-handler workload of `[server.js:L1-L14]`, none of these advantages are presently relevant, so H1 dominates H2 on simplicity grounds — H2 is documented here primarily because it is the conventional deployment pattern in production Node.js environments and reviewers should understand why it is **not** the recommended path for this specific codebase.
- **Cross-reference.** [09-optimization-recommendations.md](./09-optimization-recommendations.md) **A4-1** ("Environment-variable port parameterization") and **A3-3** ("Reverse proxy + multi-instance"). Reviewers approving H2 should consult A4-1 for the C-004 parameterization sketch and A3-3 for the proxy-architecture rationale and the constraint-relaxation discipline.

### H3. PM2 (or equivalent) multi-process orchestration

- **Tag: ADVISORY-C001 + ADVISORY-C002.**
- **Proposal.** Adopt a process-supervisor dependency — most commonly `pm2` from npm — to orchestrate multiple `node server.js` worker processes on a single host with built-in primitives for graceful restarts, log aggregation, monitoring, and zero-downtime reload. PM2's `cluster` execution mode wraps the same primary/worker pattern as H1 (cluster module) but supplies the supervision layer as an external dependency rather than as inline cluster-module code in `[server.js]`. Concretely: add `"pm2": "^5.4.0"` (or the current stable major) to the `dependencies` (or `devDependencies`) object inside `[package.json:L1-L11]`, run `npm install` to regenerate `[package-lock.json:L6-L11]`, place an ecosystem file (typically `ecosystem.config.js`) at the application root specifying `instances: 'max'` (one worker per logical CPU) and `exec_mode: 'cluster'`, and invoke `npx pm2 start ecosystem.config.js` to launch the cluster. Equivalent alternatives include `forever` and `supervisor` (both older), `nodemon` (development-only), and OS-level supervisors (`systemd`, `supervisord`, `runit`) that do not require an npm dependency; the latter would be a non-C-002 path documented under H1 or H2 rather than under H3.
- **Footprint.** Approximately zero source lines added to `[server.js]` itself if PM2's `cluster` mode is used — PM2 forks worker processes via the cluster-module machinery internally, and the worker processes each execute `[server.js]` as-is. The ecosystem-config file is a new file at the application root and counts as a C-001 modification. One direct dependency addition (`pm2`) plus its transitive footprint (typically ~30 packages — process-management primitives, log-rotation helpers, IPC, CLI parsers, telemetry) counts as a C-002 relaxation. Constraint **C-003 is not necessarily implicated** because the per-process handler at `[server.js:L6-L10]` remains single-purpose; PM2's primary process is conceptually equivalent to the cluster-module's primary, but because it lives in the `pm2` package rather than inline in `[server.js]`, the application source preserves its single-purpose posture. (Reviewers who construe C-003 to include any out-of-process orchestration MAY add ADVISORY-C003 to this entry; the analysis records the conservative reading above and notes the looser one for transparency.) Constraint **C-004 is not implicated** because PM2 does not require port parameterization — the worker processes all bind to the same port via the cluster mechanism.
- **Effect.** Similar to H1 in raw throughput lift (~3x–4x on a 4-core host) because PM2's cluster mode is built atop the same Node.js `cluster` primitive. H3 dominates H1 on operational ergonomics: PM2 provides log aggregation across workers, graceful restart with health-check gating, automatic restart on crash, daemonization (the server outlives the shell session), and a built-in CLI for inspection (`pm2 list`, `pm2 logs`, `pm2 monit`). H3 dominates H2 on simplicity: no reverse-proxy configuration is required because all workers share one port via cluster-mode socket sharing. The trade-off is the C-002 dependency footprint — PM2 is a substantial package, on the order of `pino` and `prom-client` combined, and the same vulnerability-verification discipline applies to it as to those (per chapter 11's O3/O4 security caveats). The recommendation is the most operationally complete of H1-H3 for a single-host deployment and is the canonical production-deployment pattern for Node.js HTTP services on a single VM or container host.
- **Cross-reference.** No standalone chapter-09 entry has previously been authored for PM2; reviewers approving H3 should treat this entry as the canonical write-up, with the C-001 + C-002 tag composition aligning to chapter 09's "ADVISORY-C001 + ADVISORY-C002" sub-section (the same sub-section that contains O1/O3/O4 in observability). Chapter 09's aggregation has been updated to reflect H3 as a new recommendation entry; see chapter 09 entry **A2-5** ("PM2 multi-process orchestration").

### H4. Multi-host distributed deployment

- **Tag: ADVISORY-C001 + ADVISORY-C003 + ADVISORY-C004.**
- **Proposal.** Lift the loopback binding at `[server.js:L3]` (change `'127.0.0.1'` to `'0.0.0.0'` or to a configurable host) AND parameterize the port at `[server.js:L4]` via environment variable (or accept a host-specific port set in the orchestrator's deployment manifest), and deploy `node server.js` across multiple physical or virtual hosts behind a TCP or HTTP load balancer (e.g., a hardware load balancer, an AWS Application Load Balancer, a Kubernetes Service, or a Layer-4 proxy). Each host runs one or more instances (potentially composed with H1's cluster pattern or H3's PM2 supervision per host); the load balancer distributes incoming traffic across hosts using one of the standard balancing algorithms (round-robin, least-connections, IP-hash). H4 is the canonical horizontal-scaling pattern that the words "horizontal scaling" most often refer to in production literature, and it is the only path to throughput beyond what a single physical machine's CPUs can deliver.
- **Footprint.** Two source lines at `[server.js:L3-L4]` change: the bind address (C-001 + C-004 because the host is now an environment-variable read) and the port (C-001 + C-004 because the port is now an environment-variable read). The deployment topology expands from "one host, one process" to "N hosts, multiple processes per host, a load balancer in front" — a significant **C-003** scope expansion because the system now spans multiple top-level architectural components (the load balancer, the multiple hosts, the inter-host network) rather than the single-purpose single-process posture of the original. Significant infrastructure — multiple hosts, a load balancer, network configuration, possibly a service-discovery layer — is not committed to this repository. Per `[Section 2.4.3]`, the application as written is single-host single-instance; H4 is the transformation that lifts both halves of that constraint AND introduces the cross-host orchestration layer that C-003 protects against.
- **Effect.** Enables true horizontal scaling across hosts, which is the only path to throughput beyond what a single physical machine's CPUs can deliver. The marginal cost per added host is approximately one whole-machine RPS-equivalent, modulo load-balancer overhead (typically sub-millisecond at the proxy layer for HTTP/1.1, lower for TCP balancing). Requires lifting ADR-003 per `[Section 6.5.7]`, which is the most consequential bind-side architectural decision in the application — the analysis must explicitly acknowledge that lifting ADR-003 trades the zero-external-attack-surface posture documented in `[Section 6.4]` for cross-host reachability. The recommendation should not be applied without a security review at the level of detail recommended in [11-observability-recommendations.md](./11-observability-recommendations.md) (the security-related preconditions for exposing a non-localhost service) AND without the prerequisite observability investments (at minimum O1 for per-request logging, plus O4 or O3 for cross-host distributed tracing, both of which carry their own C-002 dependency-vulnerability and PII-redaction preconditions).
- **Note on measurement.** Per AAP §0.8.1 ("Measurement isolation"), distributed load testing is structurally impossible without this change — every measurement in chapters 04, 05, 06, and 07 is from the same host as the server-under-test. H4 therefore enables both (a) production-scale traffic and (b) the more rigorous measurement methodology that would isolate the load generator from the server-under-test on separate hosts, eliminating the shared-host CPU and loopback-transport contention that the current methodology accepts. Reviewers approving H4 for production scaling should also consider whether the measurement methodology should be re-baselined on the distributed configuration before establishing new performance SLAs.
- **Cross-reference.** [09-optimization-recommendations.md](./09-optimization-recommendations.md) **A4-3** ("Multi-host distributed deployment"). A4-3 in chapter 09 carries the same combined tag set as this H4 (**ADVISORY-C001 + ADVISORY-C003 + ADVISORY-C004**) and references the same source-change pair at `[server.js:L3-L4]` plus the same C-003 scope expansion to a distributed fleet.

### Single-Process Multi-Thread Alternative (worker_threads — documented but not promoted)

- **Status: documented for completeness; not promoted as an H-series scaling recommendation.**
- Node.js's `worker_threads` module (`require('worker_threads')`) runs multiple JavaScript execution contexts within a single `node` process. Each worker thread has its own V8 isolate, its own event loop, and its own heap; threads communicate via `MessagePort` and `SharedArrayBuffer`. For a Node.js HTTP server, the typical worker-thread pattern is to have the main thread own the listening socket and dispatch accepted connections (or parsed requests) to a pool of worker threads for handler execution. Like H1, this is a single-host pattern — the listening socket is still on `127.0.0.1:3000`, so the single-instance and loopback constraints are unaffected.
- **Why not promoted.** For a static-response handler that does no CPU-heavy work — the handler at `[server.js:L7-L9]` is three statements with no JSON parse, no regex, no crypto, no template render — the overhead of marshalling requests across thread boundaries via `MessagePort` typically **exceeds** the parallelization benefit. Worker threads dominate cluster (H1) only when each request involves substantial CPU work per request that benefits from parallel execution within the same memory space (shared dictionaries via `SharedArrayBuffer`, shared caches, etc.). None of those conditions apply to `[server.js:L1-L14]`. Worker threads are therefore documented here for completeness and parity with other Node.js performance literature; **operators should prefer H1 (cluster) for HTTP scaling of this specific codebase** because it has lower per-request overhead and a lower implementation footprint for the same throughput lift.
- **If the workload changes.** Should this codebase be extended in the future to include CPU-heavy per-request work (cryptographic operations, image processing, large JSON parsing, regex evaluation against multi-kB bodies), worker_threads would become a more attractive scaling pattern; chapter 09 carries a sidebar entry (**A1-4**, "Worker-threads in-process parallelism") for that future-case use, tagged ADVISORY-C001 only. The chapter 10 H-series, however, is keyed to the static-handler workload of `[server.js:L1-L14]` as it exists today, and worker_threads is not part of the recommended H1–H4 set for that workload.

## Empirical Observations

The qualitative scaling shape expected from the single-process configuration is captured by the per-rung measurements in [05-latency-and-throughput.md](./05-latency-and-throughput.md) ("Latency by Concurrency" and "Throughput by Concurrency") and the corresponding event-loop-lag and probe-RTT measurements in [06-event-loop-and-concurrency.md](./06-event-loop-and-concurrency.md) ("Per-Rung Lag and Probe RTT"). The expected shape, against which the captured numbers should be compared once `[../../benchmarks/run-baseline.sh](../../benchmarks/run-baseline.sh)` and `[../../benchmarks/measure-event-loop-lag.sh](../../benchmarks/measure-event-loop-lag.sh)` have been executed on the target host, is the following:

- **c=1 (one persistent connection).** Throughput is bounded by single-connection round-trip latency on the loopback transport — typically a small number of hundreds of microseconds per request on modern Linux, with the resulting RPS bounded to roughly the reciprocal of mean latency. The event loop has substantial headroom; the lag p99 sits at the noise floor (single-digit microseconds in the sampler's own loop per chapter 06's c=1 interpretation). The vertical-scaling ceiling is not reached at this rung; the application is latency-bound, not throughput-bound.
- **c=10 (ten parallel connections).** Throughput climbs nearly linearly with concurrency relative to c=1 because the event loop continues to have substantial per-tick headroom — ten concurrent in-flight requests interleave on the single thread without queueing meaningfully (each request's three handler statements complete in microseconds before the next request's turn). The lag distribution remains close to the c=1 floor; the saturation point has not been reached.
- **c=100 (one hundred parallel connections).** Throughput approaches the per-process event-loop ceiling. Per chapter 06's c=100 interpretation, the lag p99 typically begins to spread relative to p50 as many requests arrive within the same tick boundary and the loop processes them serially. RPS continues to rise but with diminishing marginal returns per added connection. This is typically the rung at which the vertical-scaling ceiling becomes visible on commodity hardware — the per-process throughput floor is being approached.
- **c=1000 (one thousand parallel connections).** Throughput typically plateaus or degrades relative to c=100, depending on which kernel-side resource binds first. On hosts where the TCP listen-backlog (default 511 per the `http.Server` documentation discussed in [07-network-latency.md](./07-network-latency.md)) saturates, the kernel begins dropping SYNs or marking connections as RST-on-overflow per `tcp_abort_on_overflow`; on hosts where the process file-descriptor limit (default 1024 on Linux without `ulimit -n`) binds first, autocannon reports socket errors as the FD pool empties. Per [06-event-loop-and-concurrency.md](./06-event-loop-and-concurrency.md) ("Backlog Saturation" and "FD Pressure at c=1000"), non-zero `errors`, `timeouts`, or `non2xx` counts in `benchmarks/results/<timestamp>/autocannon-during-elag.json` at the c=1000 rung are, by elimination, evidence of TCP-layer or kernel-layer saturation rather than application-layer failure — the handler at `[server.js:L6-L10]` cannot itself produce a non-2xx response.

## Workflow-Driven Scaling Considerations

In a typical production Node.js application, scaling complexity is dominated by the cross-component coordination that user workflows require: database connection pooling and read-replica routing for query traffic, distributed cache invalidation across nodes for read-heavy workloads, background-job queue distribution (Bull, BullMQ, RabbitMQ, Kafka consumer groups) for asynchronous work, multipart-upload bandwidth provisioning for file ingest, and outbound third-party rate-limit budgeting for external integrations. **None of these subsystems exist in this codebase.** Per [02-workflow-gap-analysis.md](./02-workflow-gap-analysis.md) ("Summary Table"), seven of the eight user-named workflow categories are ABSENT: authentication flows, dashboard loading, file upload/download, third-party integrations, database queries, frontend rendering, and background job execution. The one PRESENT workflow is the static HTTP endpoint at `[server.js:L6-L10]`.

The practical implication for scaling complexity is that this application's horizontal-scaling problem is bounded by **HTTP serving alone** — no inter-component coordination is required, no shared state crosses process or host boundaries, no message-bus topology must be designed, and no idempotency or exactly-once semantics must be reasoned about. This is an unusually simple posture for a server; it means the four horizontal-scaling options above (H1–H4) can be evaluated on raw throughput grounds without the secondary considerations (cache coherence, transaction boundaries, queue ordering) that typically dominate production scaling decisions.

## Summary

- **Vertical ceiling**: a single Node.js process, executing JavaScript on a single thread per `[Section 5.2.1]`, against a single CPU core. The practical RPS ceiling is set by the event-loop's per-iteration cost for the static handler at `[server.js:L6-L10]` and is recorded empirically in [05-latency-and-throughput.md](./05-latency-and-throughput.md) once the harness has been run on the target host.
- **Single-instance ceiling**: the hardcoded port at `[server.js:L4]` and hardcoded hostname at `[server.js:L3]` together preclude a second `node server.js` instance on the same host — the second invocation fails with `EADDRINUSE` per Assumption A-002 (`[Section 2.6.1]`) and the scalability discussion in `[Section 2.4.3]`. Multi-process scaling on the same host is structurally impossible without lifting Constraint C-001 (to adopt the cluster pattern, which shares one listening socket across workers) or Constraint C-004 (to parameterize the port for multi-port-per-host deployment), and any deployment topology beyond the single in-process handler implicates Constraint C-003 ("Single-purpose") at the architectural-component level even where the per-process handler body remains byte-identical.
- **Horizontal scaling H1-H4 inventory and tags**:
    - **H1 (single-host cluster)** — ADVISORY-C001 + ADVISORY-C003. Source change to wrap `[server.js:L1-L14]` in cluster primary/worker; no dependency, no port parameterization. Expected lift ~3x–4x on a 4-core host. Lowest dependency footprint among H1-H4. Cross-references chapter 09 entry **A1-3**.
    - **H2 (single-host reverse proxy + multiple instances)** — ADVISORY-C001 + ADVISORY-C003 + ADVISORY-C004. Source change to parameterize port + reverse-proxy infrastructure; no application dependency. Expected lift comparable to H1; preferred when TLS termination, canary deployment, or rolling restart are already requirements. Cross-references chapter 09 entries **A3-3** and **A4-1**.
    - **H3 (PM2 / multi-process orchestration)** — ADVISORY-C001 + ADVISORY-C002. New ecosystem config file + `pm2` dependency; per-process `[server.js]` source is unchanged. Expected lift comparable to H1; preferred when log aggregation, graceful restart, and built-in monitoring CLI are operationally valued. Cross-references chapter 09 entry **A2-5**.
    - **H4 (multi-host distributed deployment)** — ADVISORY-C001 + ADVISORY-C003 + ADVISORY-C004. Source change to lift loopback binding + parameterize port + significant infrastructure (load balancer, multiple hosts). The only path to throughput beyond one machine's CPU capacity. Cross-references chapter 09 entry **A4-3**.
- **Among H1-H4, H1 is the lowest-friction option** because `cluster` is a Node.js built-in (no Constraint C-002 implication), the source modification is small (~15 lines added to `[server.js]`), and the expected throughput lift is near-linear with CPU core count. H1 still requires lifting Constraint C-001 (source modification) and Constraint C-003 (process-model expansion to primary/worker); but it does NOT require C-002 (no dependency) or C-004 (no port parameterization), making it the smallest constraint-relaxation footprint among the four. **H3 (PM2)** is the alternative for operators who prefer to push the supervision/monitoring complexity into a dependency rather than into `[server.js]` directly; it trades C-003 (cluster's primary/worker is in-process; PM2's is in-dependency) for C-002 (PM2 itself). **H2 and H4** require additional constraint relaxations (C-004 for port parameterization; ADR-003 for lifting the loopback binding) and additional infrastructure (reverse proxy or load balancer); they are documented for completeness and are the right answer when the architectural posture H2/H4 imply (TLS termination, multi-host) is desired regardless of throughput.
- **Worker-threads is documented but not promoted** as an H-series recommendation for this codebase, because the workload is not CPU-heavy enough to benefit from shared-memory parallelism — see the "Single-Process Multi-Thread Alternative" sub-section above for the full discussion. Chapter 09 carries it as the sidebar entry A1-4 for the future case where the workload changes.
