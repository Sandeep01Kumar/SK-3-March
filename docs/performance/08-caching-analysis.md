# Caching Analysis

The response body at `[server.js:L9]` is the 14-byte UTF-8 literal `'Hello, World!\n'`. V8 interns short string literals into its constant pool at parse time, so the JavaScript-engine cost of producing the response body on each request is effectively zero — there is no allocation, no concatenation, no template render, and no encode step that could be memoized. There is also no upstream computation whose result could be cached: per [02-workflow-gap-analysis.md](./02-workflow-gap-analysis.md) and per `[Section 5.1.4]` the server has no database query, no template render, no outbound HTTP call, and no file-system read in its per-request path; the handler at `[server.js:L6-L10]` is three statements of pure synchronous work over a compile-time constant. Application-level caching constructs (an LRU cache in front of a slow computation, a Redis cache in front of a slow database, a fragment cache in front of a rendered view) therefore have no substrate here — there is nothing slow to put behind a cache. The only category of caching that could meaningfully reduce work in this system is **HTTP-level conditional GET**, in which the server emits validator headers (`ETag` or `Last-Modified`) and freshness directives (`Cache-Control`) so that repeat clients can either skip the 14-byte body transfer (via `304 Not Modified`) or skip the request entirely (via client-side cache hit). Every option in this category requires modifying `[server.js:L7-L9]` and is therefore tagged **ADVISORY-C001** per `[README.md:L2]` and `[Section 2.6.2]` — applying any of them would violate the "Do not touch!" governance directive that Constraint C-001 protects, and is therefore conditional on the codebase owner explicitly relaxing C-001 for the specific edit.

## Why Application-Level Caching Is Not Meaningful

The standard motivations for an application-level cache are absent from this system in every dimension. Each row below names a typical cache substrate, identifies why it does not apply here, and cites the section of the report or specification that establishes the absence.

- **String constant — nothing to memoize.** `[server.js:L9]` reads `res.end('Hello, World!\n')`. The argument is a UTF-8 string literal that V8 interns at parse time and reuses across every call to the handler; the cost of "producing" the response body on each request is the cost of dereferencing a constant pool entry, which is negligible compared to socket I/O. There is no expression to evaluate, no template to render, no buffer to allocate, and no encoding step to repeat. Wrapping a memoizing cache around a constant-pool dereference is an exercise in adding code without removing work.
- **No computation — every response is byte-identical.** The handler at `[server.js:L6-L10]` reads no request data per `[Section 5.1.3]` — no `req.method`, no `req.url`, no `req.headers`, no `req.body`. Every inbound request produces the same response regardless of what the client sent. There is no per-request branch, no per-request computation, and no per-request data flow whose result could be keyed and cached.
- **No data layer — no query to cache.** Per `[Section 3.5.1]` there is no database, no key-value store, no file-system read, and no persistent state of any kind. The standard "cache database query results" pattern has no substrate; there are no queries to memoize.
- **No external API — no upstream call to cache.** Per `[Section 3.4.1]` and `[Section 5.1.4]` the server makes zero outbound network calls. The standard "cache third-party API responses" pattern has no substrate; there is no upstream service whose response would benefit from local memoization.
- **No frontend — no rendered view to cache.** Per `[Section 7]` no client-side rendering surface exists; the response content-type set at `[server.js:L8]` is `text/plain`, not HTML, JSON, or any structured format that would feed a UI layer. The standard "fragment cache" or "page cache" pattern has no substrate; there is no rendered output upstream of the wire that could be cached.

The conclusion follows directly: any "application-level cache" implementation in this codebase would be an exercise in adding cost (cache lookup overhead, memory footprint, additional code paths, additional source modification) without saving cost (because there is no expensive computation upstream of the cache to save). This chapter therefore does not propose any application-level caching recommendation — and no other chapter in this report proposes one either, including [09-optimization-recommendations.md](./09-optimization-recommendations.md) and [11-observability-recommendations.md](./11-observability-recommendations.md).

## HTTP-Level Caching Opportunities

The recommendations below are the only category of caching that could meaningfully reduce work in this system. Each one modifies the handler at `[server.js:L7-L9]` to emit additional response headers (and, for C1/C2/C4, to inspect request headers and emit a `304 Not Modified` short-circuit). Every recommendation in this section is tagged **ADVISORY-C001** because every one of them edits `[server.js]`, which is prohibited by Constraint C-001 per `[README.md:L2]` and `[Section 2.6.2]` without explicit owner relaxation of the constraint.

### C1. `ETag` + `If-None-Match` (Strong Validator)

- **Tag**: **ADVISORY-C001**
- **Proposal.** At module scope (above the `http.createServer` call at `[server.js:L6]`), compute a strong-validator ETag value once at process start — either a fixed literal such as `'"hello-v1"'` (the surrounding double-quotes are part of the strong-validator syntax per RFC 7232) or an MD5 hash of the 14-byte body buffer using `crypto.createHash('md5').update('Hello, World!\n').digest('hex')`. In the handler at `[server.js:L7-L9]`, add `res.setHeader('ETag', ETAG)` before the body write. Before emitting the body, inspect `req.headers['if-none-match']`; if it equals `ETAG`, short-circuit with `res.statusCode = 304; res.end();` instead of writing the body. The short-circuit path emits the same headers as the 200 path (so the client can re-confirm the validator) but does not write the 14-byte body.
- **Constraint to relax.** Constraint C-001 per `[README.md:L2]` and `[Section 2.6.2]`. The recommendation modifies `[server.js:L6-L10]`, adding approximately five lines: one at module scope for the `ETAG` constant, one `res.setHeader` call, two lines for the `if-none-match` inspection, and one branch to emit the 304. The recommendation is therefore not applicable for an operator who must respect C-001; it is applicable only after the codebase owner explicitly approves the source modification.
- **Effect.** On repeat requests in which the client has already cached the body and is presenting its previously stored ETag in `If-None-Match`, the server response is `304 Not Modified` with no body. The wire bytes drop from approximately 130–150 bytes (status line + three headers + 14-byte body + framing CRLFs) to approximately 80–100 bytes (status line + same three headers + framing CRLFs). The body savings of 14 bytes per repeat request is small in absolute terms, but at high cache hit rates (production browser clients revisiting the endpoint), the cumulative saving scales with the cache-hit RPS rather than the total RPS.
- **When it helps.** Clients that honor HTTP caching semantics — browsers, CDNs, well-behaved HTTP client libraries (`curl --etag-save`, `requests` with `requests-cache`, `node-fetch` with a cache wrapper). For the autocannon harness used in this report's measurements, `autocannon` does not honor caching by default — each connection is a fresh TCP socket with no client-side cache state — so applying C1 in isolation will not change the latency or throughput numbers reported in [05-latency-and-throughput.md](./05-latency-and-throughput.md). The value of C1 is realized only when production clients consume the endpoint, not when synthetic load generators do.
- **Cross-reference.** [09-optimization-recommendations.md](./09-optimization-recommendations.md), the ADVISORY-C001 caching entry referencing C1.

### C2. `Last-Modified` + `If-Modified-Since` (Weak Validator)

- **Tag**: **ADVISORY-C001**
- **Proposal.** At module scope, compute a `LAST_MODIFIED` date string formatted per RFC 7231 — for example, capture the process start time once with `const LAST_MODIFIED = new Date().toUTCString();`. In the handler at `[server.js:L7-L9]`, add `res.setHeader('Last-Modified', LAST_MODIFIED)` before the body write. Inspect `req.headers['if-modified-since']`; if the parsed client value is greater than or equal to the server's `LAST_MODIFIED`, short-circuit with `res.statusCode = 304; res.end();`. The same five-line shape as C1, but using a temporal validator rather than a content-derived validator.
- **Constraint to relax.** Constraint C-001 per `[README.md:L2]` and `[Section 2.6.2]`. Approximately five lines added to `[server.js:L6-L10]`.
- **Effect.** Functionally similar to C1 for this particular body. The semantic difference is granularity: `Last-Modified` resolves to one-second precision (the smallest unit RFC 7231 specifies), so a client that re-requests within the same second as a content change would receive a stale 304; `ETag` resolves to whatever distinguishing identifier the server chooses (a hash gives byte-level granularity, a version string gives manual-bump granularity). For an *unchanging* body — which `[server.js:L9]` is, by Constraint C-001 — both validators produce the same outcome (always 304 when the client has the latest copy) and the granularity difference is irrelevant. C2 is included in this enumeration for completeness because it is the historically older of the two mechanisms and some clients implement it but not C1.
- **When it helps.** Same client population as C1. Equally inert against the autocannon harness for the same reason.

### C3. `Cache-Control: public, max-age=…`

- **Tag**: **ADVISORY-C001**
- **Proposal.** In the handler at `[server.js:L7-L9]`, add a single line: `res.setHeader('Cache-Control', 'public, max-age=3600')` (or a longer max-age — the body is constant per Constraint C-001, so the freshness lifetime can in principle be set arbitrarily high). The `public` directive permits shared caches (proxies, CDNs) to cache the response in addition to the originating client; `max-age=3600` instructs caches to consider the response fresh for one hour before re-validating.
- **Constraint to relax.** Constraint C-001 per `[README.md:L2]` and `[Section 2.6.2]`. Exactly one line added to `[server.js:L6-L10]`; structurally the smallest of the four ADVISORY-C001 options in this section.
- **Effect.** Clients with HTTP caches may serve subsequent requests entirely from their local cache without contacting the server at all — eliminating the round trip, the TCP handshake, the request transmission, the response transmission, and all server-side work. This is the most impactful of the four client-side options when paired with a real client population because it removes work from both sides of the wire. The benchmark numbers from `autocannon` would not change because the load generator does not honor `Cache-Control`. The value, again, is realized only when production clients consume the endpoint.
- **Recommended pairing.** C3 + C1 (or C3 + C2). The `Cache-Control: max-age` directive tells the client how long the response is fresh; the `ETag`/`Last-Modified` validator tells the client how to revalidate after the max-age expires without re-downloading the body. Together they yield the optimal client behaviour: cache locally for the freshness window, then issue a conditional GET that receives a 304 if the body is unchanged. Either C3 alone or C1/C2 alone is workable; the combination is strictly better for clients.

### C4. Weak `ETag` Variant

- **Tag**: **ADVISORY-C001**
- **Proposal.** Identical to C1 in structure, but use the weak-validator syntax `W/"hello-v1"` (the `W/` prefix indicates the server is asserting semantic equivalence rather than byte-identical equivalence). All other mechanics — module-scope constant, handler `setHeader` call, `if-none-match` inspection, 304 short-circuit — are unchanged from C1.
- **Constraint to relax.** Constraint C-001 per `[README.md:L2]` and `[Section 2.6.2]`. Approximately five lines added to `[server.js:L6-L10]`, the same shape as C1.
- **Effect.** Identical to C1 for this particular body. The distinction between strong and weak validators matters only when a server might serve semantically equivalent but byte-different representations — for example, two JSON encodings of the same object with different whitespace, or two image encodings of the same picture with different metadata. The body at `[server.js:L9]` is a single fixed byte sequence and admits no semantic-but-not-byte equivalence, so the choice between C1 and C4 is purely cosmetic for this system. C4 is included for completeness; C1 is the natural default.

## Caches Outside the Application Boundary

Even without modifying `[server.js]`, an operator may interpose a caching reverse proxy — nginx, Varnish, Apache `mod_cache`, HAProxy with caching enabled, or a CDN edge — between the network and the Node.js process. Such a proxy observes the application's responses and stores them locally; subsequent requests within the proxy's cache lifetime are served from the proxy's cache without invoking the Node.js handler at `[server.js:L6-L10]` at all. From the application's perspective this is invisible — `[server.js]` continues to receive only the cache-miss subset of traffic — and from the perspective of the report's constraints (C-001 through C-004 per `[Section 2.6.2]`) this is a deployment-topology change, not a source change. It is therefore **out of scope for the application source** but **in scope for the operator's deployment topology**: the operator can apply it without lifting Constraint C-001, but the implementing agent of this analysis report cannot validate it because the application's deployment topology is outside the scope of the four committed source files.

The asymmetry is worth restating. Proxy-side caching is the highest-impact caching lever available against this system — it cuts traffic to the Node.js process by the cache hit rate — but the implementing agent of this analysis report does not deploy proxies. The operator who consumes this report does. The recommendation below is therefore tagged READY at the deployment level, with the explicit caveat that the implementing agent has not validated it and cannot quote a measured effect.

### C5. CDN / Reverse Proxy Caching (Deployment-Level)

- **Tag**: **READY** (deployment-level — no application change)
- **Proposal.** Deploy nginx (or Varnish, or HAProxy with caching, or a CDN edge) in front of the Node.js process at `127.0.0.1:3000` per `[server.js:L3]` and `[server.js:L4]`. Configure the proxy to cache the `/` response with a fixed TTL — for example, in nginx, a `proxy_cache_path` directive plus a `proxy_cache_valid 200 60s` directive in the relevant `location` block, yielding 60-second cache duration. Because the server emits no `Cache-Control` header in its default form per `[server.js:L7-L9]`, the proxy will not infer a cache lifetime from the response itself; the operator must configure the lifetime at the proxy level.
- **Constraint to relax.** None at the application level — `[server.js]`, `[package.json]`, `[package-lock.json]`, and `[README.md]` all remain byte-identical. C-001 is not lifted. C-002 is not lifted. C-003 is not lifted (the application's purpose is unchanged from its perspective; the proxy is an external system). C-004 is not lifted. The recommendation lives entirely outside the four committed source files.
- **Effect.** The Node.js process at `[server.js:L1-L14]` receives only the cache-miss subset of inbound traffic. At a steady-state cache hit rate of `h` (where `0 ≤ h ≤ 1`), the server's RPS load drops to `(1 − h) × incoming_rps`; the proxy serves the cache-hit fraction `h × incoming_rps` from its local copy without involving Node.js. For a workload of repeat requests against the single endpoint at `/`, the cache hit rate approaches `1` after the first cache-miss request populates the proxy's cache, so the proxy effectively absorbs all but a vanishingly small fraction of the load. This is the most impactful "caching" option available against this system; it is also the only one that does not require lifting Constraint C-001.
- **Caveat — operational scope.** The recommendation requires the operator to deploy, configure, and manage a reverse proxy or CDN — work that is operationally non-trivial and outside the scope of this repository. The implementing agent of this report has not validated the recommendation empirically; the harness at `[benchmarks/run-baseline.sh](../../benchmarks/run-baseline.sh)` drives autocannon directly against `127.0.0.1:3000` without an interposed proxy, so the measurements in [05-latency-and-throughput.md](./05-latency-and-throughput.md) and [06-event-loop-and-concurrency.md](./06-event-loop-and-concurrency.md) reflect the unproxied configuration. A future harness extension that interposed a proxy and re-measured would produce different (smaller) RPS numbers at the Node.js process while reporting much higher RPS numbers at the proxy's listening port — the workload would be shifted, not eliminated.
- **Caveat — interaction with C1/C2/C3/C4.** A reverse-proxy cache is more effective when the application emits `Cache-Control` and `ETag`/`Last-Modified` headers (i.e., when C1+C3 or C2+C3 are also applied) because the proxy can then key its cache on the validators and revalidate against the origin only when its local copy expires. Without those headers, the proxy uses its own configured TTL exclusively, which is workable but less precise. For an operator who controls both the proxy configuration and the application source, the combination of C3 + (C1 or C2) on the application side and `proxy_cache` on the proxy side is the strongest configuration available; it requires lifting C-001 for the application-side changes and is therefore mixed-tag (READY for the proxy, ADVISORY-C001 for the application).

## Quantitative Estimate

The 14-byte response body at `[server.js:L9]` represents a small fraction of the per-response wire bytes. A typical HTTP/1.1 response from the handler at `[server.js:L7-L9]` consists of: the status line `HTTP/1.1 200 OK\r\n` (approximately 17 bytes); three response headers — `Content-Type: text/plain\r\n` (approximately 27 bytes per `[server.js:L8]`), a `Date:` header (approximately 38 bytes, emitted by Node.js's HTTP library by default), and a `Connection:` header (approximately 22 bytes when keep-alive is in use); a blank-line separator (`\r\n`, 2 bytes); and the 14-byte body. Summing yields approximately 120 bytes per response, of which the body is 14 bytes — roughly 12% of the total. Switching the body from 14 bytes to 0 bytes (via `304 Not Modified` per C1/C2/C4) therefore saves approximately 10–12% of wire bytes per repeat request. The CPU savings on the server side — skipping the call to `res.end('Hello, World!\n')` and the corresponding socket write — are smaller in absolute terms than the wire-byte savings because the handler at `[server.js:L7-L9]` is already minimal; the dominant per-request cost remains the kernel-side socket I/O and the V8 HTTP parser, both of which still execute for the 304 path.

At the c=1000 rung of the concurrency ladder defined in [03-load-profile-and-methodology.md](./03-load-profile-and-methodology.md), sustained for 30 seconds, the bytes/sec savings under hypothetical C1+C3 adoption is bounded above by the gross bytes/sec figure recorded in [05-latency-and-throughput.md](./05-latency-and-throughput.md) multiplied by approximately 0.10. The precise value depends on the cache hit rate of the client population: at 100% cache hits (every request after the first served as 304), the savings approach the upper bound; at 0% cache hits (every request transferring the full body, as autocannon does today), the savings are zero. C3 alone — adding `Cache-Control: public, max-age=3600` per the C3 entry above — yields a stronger upper bound because the cache-hit requests are eliminated from the wire entirely rather than being served as smaller 304 responses; the upper bound becomes approximately 100% of the bytes/sec figure, modulated by the same cache hit rate.

The precise empirical effect of any of C1 through C4 — individually or combined with C3 — MUST be measured after applying the relevant source change in a hypothetical, constraint-lifted variant of `[server.js]`. The implementing agent of this report does not produce such measurements because Constraint C-001 per `[README.md:L2]` prohibits the source change required to enable them. The estimates in this section are therefore upper bounds derived from byte arithmetic and should not be interpreted as production figures; they are sized for order-of-magnitude reasoning and not for capacity planning.

## Summary

The table below restates the five recommendations introduced in this chapter. Recommendations C1 through C4 modify `[server.js:L7-L9]` and are therefore tagged **ADVISORY-C001** — they are applicable only after the codebase owner explicitly relaxes Constraint C-001 per `[README.md:L2]` and `[Section 2.6.2]`. Recommendation C5 lives entirely outside the four committed source files and is tagged **READY** at the deployment level, with the caveat that it requires the operator to deploy and manage a reverse proxy or CDN — work that is outside the scope of this analysis report.

| ID | Recommendation | Tag | Source lines | Effect |
|----|----------------|-----|--------------|--------|
| C1 | `ETag` + `If-None-Match` (strong validator) | ADVISORY-C001 | ~5 in `[server.js:L6-L10]` | 304 for repeat clients; ~14-byte body savings per cache-hit request |
| C2 | `Last-Modified` + `If-Modified-Since` (weak validator) | ADVISORY-C001 | ~5 in `[server.js:L6-L10]` | Same as C1 with second-level granularity instead of byte-level |
| C3 | `Cache-Control: public, max-age=…` | ADVISORY-C001 | 1 in `[server.js:L6-L10]` | Client-side caching; eliminates the round trip on cache hit |
| C4 | Weak `ETag` variant (`W/"hello-v1"`) | ADVISORY-C001 | ~5 in `[server.js:L6-L10]` | Same as C1 with weak-validator semantics; cosmetic difference only |
| C5 | CDN / reverse-proxy caching (deployment-level) | READY (deployment) | 0 in app source | Proxy-side caching; highest impact and the only option that does not require lifting C-001 |

Two top-level observations close the chapter. **First**, the highest-impact caching lever (C5 — reverse-proxy caching) is the only one that does not require lifting Constraint C-001; it is therefore the natural first recommendation for an operator who must respect the "Do not touch!" directive per `[README.md:L2]`. **Second**, the four application-side recommendations (C1 through C4) are real but small in absolute terms — the body they protect from re-transmission is only 14 bytes per `[server.js:L9]` — and their value is realized only against client populations that honor HTTP caching semantics, which the autocannon harness used in this report's measurements does not. Reviewers consuming this chapter should weight C5 above C1–C4 for any deployment that admits a reverse proxy, and should weight C1+C3 above C2 or C4 for any owner-approved application-side change because that pairing combines client-side freshness with conditional revalidation in the smallest source diff. The chapter does not propose any application-level (non-HTTP) caching recommendation because, per the "Why Application-Level Caching Is Not Meaningful" section above, no application-level cache substrate exists in this system.
