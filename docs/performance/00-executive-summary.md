# Executive Summary

Performance analysis of `[server.js:L1-L14]`. See [README.md](./README.md) for the chapter map and reproduction instructions.

## TL;DR

The application under analysis is the 14-line static-response HTTP server defined in `[server.js:L1-L14]` — a Node.js process that binds `127.0.0.1:3000` per `[server.js:L3-L4]` and returns a 14-byte `text/plain` `'Hello, World!\n'` body per `[server.js:L9]` on every request. The codebase is governed by the immutability directive at `[README.md:L2]` ("Do not touch!") codified as Constraint **C-001** per `[Section 2.6.2]`; the analysis is therefore observational and no source modifications were performed. **7 of 8 workflow categories are ABSENT** from the codebase — authentication, dashboard rendering, file upload/download, third-party integrations, database queries, frontend rendering, and background job execution — per the canonical record in [02-workflow-gap-analysis.md](./02-workflow-gap-analysis.md); only the static HTTP endpoint is PRESENT. The dominant READY recommendation is **R1** (kernel `net.core.somaxconn` tuning); every source-touching recommendation is tagged **ADVISORY-Cxxx** pending owner approval.

## Top 3 READY Recommendations

The recommendations below are applicable as-is without requiring the codebase owner to lift any of Constraints C-001 through C-004. Each is copied from [09-optimization-recommendations.md](./09-optimization-recommendations.md) ("READY Recommendations") and tagged **READY**.

1. **READY** — **R1: Tune the kernel TCP listen-backlog (`net.core.somaxconn`)** (source: [07-network-latency.md](./07-network-latency.md), aggregated as R1 in [09-optimization-recommendations.md](./09-optimization-recommendations.md)). The Node.js default listen-backlog is 511; on Linux distributions whose `net.core.somaxconn` defaults to 128, the effective backlog is capped at 128 and an autocannon c=1000 burst exceeds it. Proposed change: `sudo sysctl -w net.core.somaxconn=4096` (transient) or write `net.core.somaxconn = 4096` to `/etc/sysctl.d/99-backlog.conf` (persistent). Expected effect: reduces or eliminates SYN drops and `accept()`-queue overflows at the c=1000 rung; observable as a reduction (often to zero) in autocannon `errors` and `non2xx` counts and the elimination of `dmesg` "possible SYN flooding on port 3000" warnings. Modifies no source file, no dependency, no handler, and no config — Constraints C-001 through C-004 are all preserved.

2. **READY** — **R2: Raise the process file-descriptor limit before measurement** (source: [06-event-loop-and-concurrency.md](./06-event-loop-and-concurrency.md) "FD Pressure at c=1000" and [07-network-latency.md](./07-network-latency.md) N4, aggregated as R2 in [09-optimization-recommendations.md](./09-optimization-recommendations.md)). On many Linux distributions the default soft FD limit is 1024, which the c=1000 rung trivially exceeds once stdio, the listening socket, and concurrent client connections are accounted for — producing `EMFILE: too many open files` errors that are easy to confuse with backlog saturation. Proposed change: `ulimit -n 65535` per shell session (or `LimitNOFILE=65535` for a systemd unit, or `--ulimit nofile=65535:65535` for Docker). Expected effect: prevents `EMFILE` errors at the c=1000 rung; produces a clean latency histogram at the upper concurrency tier; removes the most common environmental confound that obscures the application's true event-loop saturation behaviour. Per-shell or per-unit change; no application file is modified.

3. **READY** — **R3: Extend the harness with additional concurrency rungs** (source: [03-load-profile-and-methodology.md](./03-load-profile-and-methodology.md) "Concurrency Ladder" and [05-latency-and-throughput.md](./05-latency-and-throughput.md) "RPS Curve and Saturation", aggregated as R3 in [09-optimization-recommendations.md](./09-optimization-recommendations.md)). The canonical four-rung ladder (1 → 10 → 100 → 1000) is geometric 10× and deliberately coarse; the saturation knee can fall anywhere between c=100 and c=1000, and on fast multi-core hosts may not appear at c=1000 at all. Proposed change: extend [`../../benchmarks/load-profile.json`](../../benchmarks/load-profile.json) with intermediate rungs (e.g., c=200, c=400, c=600, c=800) for saturation-knee resolution and/or super-high rungs (e.g., c=2000, c=5000, c=10000) for post-saturation behaviour. Expected effect: better resolution of the saturation knee on the RPS-vs-concurrency curve; a more defensible answer to "what is the maximum sustainable RPS on this host?" than the four-rung ladder alone can provide. Modifies only the harness package under [`../../benchmarks/`](../../benchmarks/); no application file is touched.

Additional READY items (full inventory in [09-optimization-recommendations.md](./09-optimization-recommendations.md)) include **R4** (run on the highest stable Node.js LTS), **R5** (record run manifests alongside results), **R6** (`net.ipv4.tcp_max_syn_backlog` tuning), **R7** (optional TCP Fast Open), **R8** (sample `process.memoryUsage()` via inspector protocol), **R9** (back-to-back heap-profile diffing), **R10** (record explicit `startup_time_ms`), **R11** (passive `ss -ltn` `Recv-Q` sampler), **R12** (1-second RSS/CPU sampling via `pidstat`/`ps`), and **R13** (deploy a CDN or reverse-proxy cache in front of the application).

## Top 5 ADVISORY Recommendations

The recommendations below each require the codebase owner to lift one or more of Constraints C-001 through C-004 per `[Section 2.6.2]` before they can be applied. Each is copied from [09-optimization-recommendations.md](./09-optimization-recommendations.md) with the constraint(s) that must be relaxed named explicitly. None of these recommendations is presently applicable; they are listed here so the codebase owner has a constraint-aware inventory.

1. **ADVISORY-C001** — **A1-1: Add HTTP caching headers (`ETag`, `Last-Modified`, `Cache-Control`)** (source: [08-caching-analysis.md](./08-caching-analysis.md) C1–C4, aggregated as A1-1 in [09-optimization-recommendations.md](./09-optimization-recommendations.md)). Finding: the response at `[server.js:L9]` is a 14-byte compile-time constant for which HTTP-level conditional GET would reduce wire bytes to zero for repeat-client requests. Proposed change: approximately 5 added lines centred at `[server.js:L7-L9]` to set `ETag` / `Cache-Control` headers and short-circuit on `If-None-Match`. **Constraint to relax: C-001** per `[README.md:L2]` and `[Section 2.6.2]` — modifies `[server.js]`. Expected effect: 304 Not Modified responses with no body for repeat-client requests; combined with `Cache-Control` directives, the round-trip itself is eliminated for the configured TTL; prerequisite for getting full value out of R13 (proxy-side caching).

2. **ADVISORY-C001 + ADVISORY-C003** — **A1-3: Adopt Node.js's `cluster` module to fork one worker per CPU core** (source: [06-event-loop-and-concurrency.md](./06-event-loop-and-concurrency.md) "Event-Loop Saturation Signature" and [10-scalability-assessment.md](./10-scalability-assessment.md) H1, aggregated as A1-3 in [09-optimization-recommendations.md](./09-optimization-recommendations.md)). Finding: the application is single-threaded per `[Section 5.2.1]` and uses exactly one CPU core regardless of host capacity; the `cluster` module forks N worker processes that share the listening socket via `SO_REUSEPORT`. Proposed change: approximately 12 added lines that wrap `[server.js:L6-L14]` in a primary/worker pattern. **Constraints to relax: C-001** (rewrites `[server.js:L1-L14]`) and **C-003** (introduces a primary/worker process distinction that expands the server's single-purpose scope) per `[Section 2.6.2]`. Expected effect: throughput scales near-linearly with physical core count (typically 6×–8× the single-process baseline on an 8-core host); the c=1000 saturation tail is dramatically reduced because the workload is distributed across N event loops.

3. **ADVISORY-C002 + ADVISORY-C001** — **A2-2: Add structured request logging via `pino`** (source: [11-observability-recommendations.md](./11-observability-recommendations.md) O1, aggregated as A2-2 in [09-optimization-recommendations.md](./09-optimization-recommendations.md)). Finding: the application currently emits exactly one log line — the startup `console.log` at `[server.js:L13]`; there is no per-request log, no error log, and no forensic surface. Proposed change: add `pino` to `[package.json:L1-L11]` `dependencies` and approximately 2 added lines to the handler at `[server.js:L6-L10]` to emit one NDJSON log line per request with method, URL, status, and duration. **Constraints to relax: C-002** (adds a single application dependency) and **C-001** (modifies `[server.js:L6-L10]`) per `[Section 2.6.2]`. Expected effect: per-request NDJSON log line ready for direct ingestion by Loki, Elasticsearch, Splunk, or any line-oriented log collector; negligible CPU/memory overhead on the per-request path. **Pre-deployment caveats** (canonical text in chapter 09 A2-2): mandatory `npm audit` + `osv.dev` check before C-002 relaxation, AND mandatory pino `redact` configuration for credential-bearing headers (`Authorization`, `Cookie`, `Proxy-Authorization`, `X-API-Key`) plus query-string credential deny-list applied to `req.url` before logging.

4. **ADVISORY-C002 + ADVISORY-C001 + ADVISORY-C003** — **A2-4: Add `prom-client` for Prometheus `/metrics` exposition** (source: [11-observability-recommendations.md](./11-observability-recommendations.md) O2, aggregated as A2-4 — the single canonical entry — in [09-optimization-recommendations.md](./09-optimization-recommendations.md); cross-referenced as A3-2 in chapter 09's ADVISORY-C003 section, not a duplicate). Finding: Prometheus is the de-facto cloud-native metrics standard but the application has no metrics surface at all. Proposed change: add `prom-client` to `[package.json:L1-L11]` `dependencies`; instrument the handler with a counter and latency histogram (~5 added lines); branch on `req.url === '/metrics'` to return `register.metrics()` (~5 added lines). **Constraints to relax: C-002** (single dependency), **C-001** (modifies `[server.js:L6-L10]`), and **C-003** (adds a `/metrics` URL branch — a routing decision) per `[Section 2.6.2]` — all three are non-negotiable for this recommendation. Expected effect: Prometheus-compatible `/metrics` endpoint exposing request counters, latency histograms, status-code histograms, and default Node.js process metrics (event-loop lag, GC pauses, heap stats) — the canonical operational signal source for Grafana / Alertmanager dashboards and alerts. **Pre-deployment caveat**: mandatory `npm audit` + `osv.dev` check at the time of install, per chapter 09 A2-4.

5. **ADVISORY-C001** — **A1-5: Pass an explicit `backlog` argument to `server.listen(...)`** (source: [07-network-latency.md](./07-network-latency.md) N5, aggregated as A1-5 in [09-optimization-recommendations.md](./09-optimization-recommendations.md)). Finding: the kernel-level R1 (`net.core.somaxconn`) tuning above only takes effect if the listening socket also requests a `backlog` at least as large; per the Linux `listen(2)` semantics, the effective backlog is `min(application_backlog, net.core.somaxconn)`. The current `[server.js:L12]` invokes `server.listen(port, hostname, callback)` without an explicit backlog and accepts the Node.js default of 511. Proposed change: modify `[server.js:L12]` to `server.listen({ port, host: hostname, backlog: 4096 }, callback)` (or the positional `server.listen(port, hostname, 4096, callback)` form). **Constraint to relax: C-001** per `[README.md:L2]` and `[Section 2.6.2]` — modifies `[server.js:L12]`. Expected effect: aligns the application-side accept-queue cap with the kernel-side cap after R1 is applied; useful **only after R1** — without R1, the kernel cap still binds and increasing the application-side backlog above the kernel cap has no effect.

## Governance Constraints in Force

Every recommendation in this analysis was classified against the four constraints below; the constraint label on each ADVISORY entry above names the specific governance directive that the codebase owner must explicitly lift before that entry can be applied. The constraint definitions are reproduced from [README.md](./README.md) ("Constraints") and `[Section 2.6.2]`; this section is a one-line reminder for readers consuming this executive summary as their only touchpoint with the report.

- **C-001** — "Do not touch!" — no application-source modification — `[README.md:L2]`, `[Section 2.6.2]`. `server.js`, `package.json`, `package-lock.json`, and `README.md` are read-only.
- **C-002** — Zero application dependencies — `[Section 2.6.2]`. The application package's `[package.json:L1-L11]` carries an empty `dependencies` / `devDependencies` graph (`[package-lock.json:L6-L11]`); the measurement harness at [`../../benchmarks/`](../../benchmarks/) lives in a separate npm package precisely to preserve this constraint.
- **C-003** — Single-purpose server — `[Section 2.6.2]`. The handler at `[server.js:L6-L10]` returns a fixed 14-byte `text/plain` response for every request; no routes, middleware, or alternate response paths may be added.
- **C-004** — Hardcoded configuration — `[Section 2.6.2]`. The hostname `[server.js:L3]`, port `[server.js:L4]`, and response body `[server.js:L9]` remain literals; no environment variables, `.env` files, or runtime parameters may be introduced.
