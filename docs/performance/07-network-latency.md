# Network Latency

Because `[server.js:L3]` binds the listener to `127.0.0.1` — the IPv4 loopback interface — wide-area network latency does not enter the measurement picture at all. Every byte that traverses the wire between the load generator and the server traverses the kernel's loopback adapter, which is implemented entirely in software and does not touch any network interface card, switch, or router. There is no link-layer framing across a physical medium, no propagation delay across a cable, no queueing at an intermediate device, and no wide-area path that could be congested by other tenants on a shared network. All measurement is intra-host, and all latency numbers reported in this report are therefore loopback latency numbers — a lower bound, not a production estimate. This chapter characterizes (a) the loopback round-trip baseline that establishes the kernel-and-CPU floor against which the handler at `[server.js:L6-L10]` is measured; (b) the default TCP listen-backlog implicitly chosen by `[server.js:L12]` and the kernel-level cap on it set by `net.core.somaxconn`; (c) the kernel-tunable advisories — tagged **READY** because they are external to the application and require no source-code modification — that become relevant when the c=1000 rung of the concurrency ladder defined in [03-load-profile-and-methodology.md](./03-load-profile-and-methodology.md) ("Concurrency Ladder") approaches the backlog limit; and (d) the single application-level recommendation tagged **ADVISORY-C001** because it would require modifying `[server.js:L12]` and therefore relaxing Constraint C-001 per `[README.md:L2]` and `[Section 2.6.2]`.

## Loopback Round-Trip Baseline

The fastest possible HTTP request-response cycle on this host is one in which the TCP three-way handshake, the request-line framing, the (empty) request body parse, the handler dispatch, and the response framing all complete with zero contention. On modern Linux kernels, the kernel-side floor of this cycle is sub-100 microseconds — the loopback driver copies bytes between sockets in the same address-space-equivalent pathway, the scheduler context-switches between the client and server processes once per request, and the TCP state machine executes its handshake steps as straight-line code with no I/O wait. Two independent measurements approximate this floor: (a) `ping 127.0.0.1` records only the ICMP echo round-trip, which is a strict lower bound on HTTP RTT because it excludes the TCP handshake, the HTTP framing, and any application-layer dispatch; (b) a Node.js client-side micro-benchmark of the form `node -e "const t = require('perf_hooks').performance.now(); require('http').get('http://127.0.0.1:3000/', () => console.log(require('perf_hooks').performance.now() - t))"` brackets a full HTTP GET against the running server and includes the per-request handler work at `[server.js:L7-L9]`. The difference between (b) and (a) is approximately the per-request handler cost — typically a few tens of microseconds for the three-statement handler at `[server.js:L7-L9]` (status assignment, header set, body write), all of which complete synchronously inside one event-loop tick per `[Section 5.2.1]`.

The empirical floor for the running server is captured in `benchmarks/results/<timestamp>/autocannon-1.json` — the c=1 rung of the concurrency ladder. At c=1, autocannon sustains one TCP connection for the 30-second measured window and pipelines requests across that one connection. The p50 latency reported by autocannon for this rung approximates the round-trip floor plus the per-request handler cost — that is, the c=1 p50 is the *system* floor, not just the *network* floor. The two-decimal-place millisecond p50 number recorded in the per-rung latency table at [05-latency-and-throughput.md](./05-latency-and-throughput.md) ("Latency by Concurrency") for c=1 is the canonical lower bound for the entire report; no application-side optimization can reduce a latency number below the c=1 p50 because that latency is dominated by transport and kernel scheduling rather than by anything the application does. A useful sanity check: if the c=1 p50 measured on the target host is materially above sub-millisecond — say, above 1 ms — then either the host is under unrelated CPU pressure during the measurement (recorded in the harness manifest), or the Node.js runtime on this host is unexpectedly slow (which would be a finding in its own right), or the autocannon configuration is incurring per-request overhead that the methodology chapter has not accounted for. In any of these cases the implementing agent records the observation rather than treating the high number as the application's fault.

The implication of the sub-100-µs loopback floor is direct and consequential: **at the lowest concurrency tier, latency is dominated by transport, not by application logic.** Any per-request optimization in `[server.js:L6-L10]` — for example, removing a header assignment, pre-computing the response body once at module load, or replacing `setHeader` with a manual `writeHead` — would shave time off only the handler portion of the c=1 latency, which is already minimal. The arithmetic is unforgiving: if the handler accounts for, say, 20 µs of a 200-µs total c=1 latency, an optimization that halved handler time would reduce the c=1 p50 by at most 10 µs (i.e., from 200 µs to 190 µs). At c=100 and c=1000, where queueing on the single-threaded event loop dominates per [06-event-loop-and-concurrency.md](./06-event-loop-and-concurrency.md) ("c=1000 — saturation candidate"), the proportion changes: handler time is multiplied by queue depth and a per-request optimization can have a multiplicative effect. The c=1 number, however, is the network-and-kernel floor, and per-request handler optimization is not where latency is to be reclaimed at that tier.

## TCP Listen-Backlog

`[server.js:L12]` invokes `server.listen(port, hostname, callback)` with the form `server.listen(3000, '127.0.0.1', () => { ... })`. The Node.js `net.Server.listen` API is overloaded; in the three-positional-arguments form used here, the `backlog` parameter is omitted, and Node.js falls back to its internal default. The default value Node.js uses when no explicit backlog is supplied is **commonly cited as 511** in the Node.js `http.Server`/`net.Server` documentation for current major versions; that figure is treated as an **inferred claim per AAP §0.9.1** ("Inferred claims") for the purposes of this chapter, because the exact integer is a runtime-version-dependent moving target. Historical and current Node.js source has documented at least two values: 128 (older Node.js majors) and 511 (newer Node.js majors). The implementing agent should verify the exact value against the Node.js version recorded in the run manifest at `benchmarks/results/<timestamp>/run-manifest.json` — the canonical place to look is the `net.Server.listen` section of the Node.js documentation for that specific major version — and update this chapter with the verified integer alongside a citation. Until verified, downstream chapters that quote 511 (notably [05-latency-and-throughput.md](./05-latency-and-throughput.md) "Comparison Against the Implicit SLA" and [06-event-loop-and-concurrency.md](./06-event-loop-and-concurrency.md) "Backlog Saturation") inherit the same provisional status.

The kernel imposes an additional cap on top of whatever value Node.js requests. On Linux, the listen-accept queue — the queue that holds fully established TCP connections waiting to be `accept()`-ed by the application — is sized by `min(backlog_argument_from_listen, net.core.somaxconn)`. The `net.core.somaxconn` sysctl reads on most modern distributions to either **4096** (recent kernels and recent stable distributions, which raised the default specifically because the previous default was a bottleneck for high-concurrency servers) or **128** (older kernels and older long-term-support distributions). The effective backlog the kernel actually enforces is therefore the minimum of what Node.js asks for (the inferred 511 above) and what the host kernel allows (typically 128 or 4096). On a host where `somaxconn=128`, the application's effective backlog is 128 regardless of Node.js's default — the kernel silently clamps. On a host where `somaxconn=4096`, the application's effective backlog is whatever Node.js requested, because Node.js's default is the smaller of the two. The operator can inspect the current value with `sysctl net.core.somaxconn` or `cat /proc/sys/net/core/somaxconn`; the value should be recorded alongside other host metadata in the run manifest so that the per-rung saturation analysis at [06-event-loop-and-concurrency.md](./06-event-loop-and-concurrency.md) ("Backlog Saturation") has access to the host-specific effective backlog.

The failure mode is precise. When the rate of new TCP SYN arrivals from autocannon's c=1000 connection ramp-up exceeds the rate at which the application calls `accept()` to drain the listen-accept queue, the queue fills. Once full, the kernel has two configurable behaviours, both governed by `net.ipv4.tcp_abort_on_overflow`: with the default `tcp_abort_on_overflow=0`, the kernel silently drops the incoming SYN (the client sees no SYN-ACK and eventually retransmits or gives up after its retry budget is exhausted); with `tcp_abort_on_overflow=1`, the kernel actively sends a RST, causing the client to fail immediately with a connection-reset error. Both behaviours surface in autocannon's output but in different fields: silent SYN drops typically manifest as autocannon `timeouts` (the client gave up after waiting), while active RST manifests as `errors` (the client's socket was reset). Non-2xx HTTP responses (`non2xx`) are **not** a backlog-saturation symptom for this server because the handler at `[server.js:L7]` unconditionally writes status 200 and the body at `[server.js:L9]` is a 14-byte compile-time constant — there is no application-level branch that could produce a non-2xx response per `[Section 5.1.3]`. Therefore at c=1000, any non-zero value in `errors`, `timeouts`, or `non2xx` reported by autocannon is, by elimination, a TCP-layer or kernel-layer phenomenon rather than an application-layer failure. The harness's c=1000 rung is the most likely scenario in this report to exhibit backlog saturation — c=100 is comfortably below any reasonable backlog limit, and c=10 and c=1 are not even close.

## Detecting Backlog Saturation

A reviewer who is trying to determine whether a particular c=1000 measurement was affected by backlog saturation has three independent signals available; the symptoms below are diagnostically complementary, and a complete saturation finding triangulates from at least two of them rather than relying on any one alone.

- **Symptom 1 — autocannon counts non-zero in `errors`, `timeouts`, or `non2xx`.** The c=1000 result file at `benchmarks/results/<timestamp>/autocannon-1000.json` is the primary evidence. The fields to inspect are `errors` (socket errors such as RST or `ECONNREFUSED`), `timeouts` (autocannon's per-request timeout fired), and `non2xx` (HTTP responses with status outside the 200-range). For the static handler at `[server.js:L6-L10]`, any non-zero value in any of these three fields at c=1000 is — by the elimination argument established in the previous section — evidence of TCP-layer or kernel-layer saturation rather than application failure. The harness's `[../../benchmarks/run-baseline.sh](../../benchmarks/run-baseline.sh)` captures `autocannon-1000.json` as part of every run, so this symptom is observable post-hoc by re-reading the archived JSON; the operator does not need to be watching live during the run.

- **Symptom 2 — `ss -ltn` shows non-zero `Recv-Q` for port 3000.** On Linux, `ss -ltn` (or the older `netstat -ltn`) enumerates listening TCP sockets and shows the current depth of the listen-accept queue in the `Recv-Q` column for each `LISTEN`-state socket. For a server that is keeping up with incoming SYNs, `Recv-Q` is approximately zero — incoming SYNs are accepted nearly as fast as they arrive. For a server whose listen-accept queue is filling, `Recv-Q` rises toward the effective backlog cap (see the previous section). Sustained `Recv-Q > 0` for the `127.0.0.1:3000` listener — particularly approaching the `min(node_default_backlog, somaxconn)` ceiling — is the most direct on-host evidence of backlog pressure. Because `Recv-Q` is a current-instant snapshot rather than a logged value, this symptom must be observed **during** a c=1000 run by an operator manually running `watch -n 0.5 'ss -ltn sport = :3000'` or equivalent in a separate terminal; the harness does not currently capture this signal.

- **Symptom 3 — kernel log shows SYN-flood warning.** The Linux kernel emits a message to the kernel log (`dmesg`) of the approximate form `TCP: request_sock_TCP: Possible SYN flooding on port 3000. Sending cookies.` when the half-open connection backlog (governed by `net.ipv4.tcp_max_syn_backlog`) overflows. The message is named after SYN-flood attacks but is benign in this context — it indicates only that SYNs are arriving faster than the kernel completes three-way handshakes, which is the legitimate behaviour of the harness's c=1000 ramp-up. Observing this message during a c=1000 run is corroborating evidence of high-concurrency saturation; observing it during c=10 or c=100 would be a surprising finding. The operator inspects this signal by running `dmesg -T --since='1 minute ago' | grep -i 'syn flooding'` (or `journalctl -k --since='1 minute ago' | grep -i 'syn flooding'` on systems with systemd) immediately after a c=1000 run completes.

The harness's `[../../benchmarks/run-baseline.sh](../../benchmarks/run-baseline.sh)` automatically captures symptom 1 (the autocannon JSON is archived per run). Symptoms 2 and 3 require manual observation by the operator during or immediately after a c=1000 run, and the absence of those observations in the archived results does not mean they were absent during the run — it only means they were not recorded. A future harness extension (tagged **READY** and tracked in [09-optimization-recommendations.md](./09-optimization-recommendations.md) as **R11** — "Add a `net.core.somaxconn` / FD-limit pre-flight check and a `ss -ltn Recv-Q` passive sampler to the harness") could add a passive `ss -ltn` sampler that snapshots `Recv-Q` at 200 ms intervals during the measured window and writes the result alongside the autocannon JSON; that would close the observability gap without requiring application-level changes. R11 is distinct from **R1** (the kernel tuning recommendation that *sets* `net.core.somaxconn` to 4096) — R11 is observability of the value; R1 is the value itself.

## Kernel-Level Tuning (READY)

The recommendations below are tagged **READY** because they are external to the application — they modify the host operating system's sysctl tunables and per-process resource limits, never `[server.js]`. Applying them requires no source-code change, no dependency change, no scope change, and no configuration-parameterization change; in particular, none of Constraints C-001 through C-004 per `[Section 2.6.2]` need be relaxed for an operator to apply them. Each recommendation is keyed by a chapter-local identifier (N1 through N4) and cross-referenced from the aggregated recommendations chapter [09-optimization-recommendations.md](./09-optimization-recommendations.md).

### N1. Raise `net.core.somaxconn`

- **Tag**: **READY**
- **Symptom that triggers this recommendation.** The c=1000 rung of the autocannon ladder, captured at `benchmarks/results/<timestamp>/autocannon-1000.json`, reports a non-zero count in `errors`, `timeouts`, or `non2xx` (per Symptom 1 above), and/or the operator observes sustained `Recv-Q > 0` for the `127.0.0.1:3000` listener via `ss -ltn` (per Symptom 2), and/or `dmesg` reports SYN flooding on port 3000 (per Symptom 3). Any one of these is sufficient; two or more in combination strengthen the finding.
- **Action — transient (loss on reboot).** `sudo sysctl -w net.core.somaxconn=4096`. The change takes effect immediately for new `listen()` calls but does not survive a reboot.
- **Action — persistent (survives reboot).** Create or edit `/etc/sysctl.d/99-backlog.conf` and add the line `net.core.somaxconn = 4096`; then run `sudo sysctl --system` (or reboot) to apply. The convention `99-` prefix ensures this file is read late in the sysctl-conf ordering so it overrides earlier defaults set by distribution packages.
- **Action — verification.** Run `sysctl net.core.somaxconn` and confirm the output reads `net.core.somaxconn = 4096`. Then restart the server (the kernel cap is read at `listen()` time, not lazily, so a running server retains the old cap until restarted) and re-run the c=1000 rung; the symptoms above should now be absent.
- **Effect.** Increases the kernel-imposed cap on the listen-accept queue from the default (commonly 128 on older long-term-support distributions; commonly 4096 on recent stable distributions, in which case this recommendation is a no-op confirming the current value rather than a change) to 4096. Once the cap is at 4096 and Node.js's default backlog remains the inferred 511, the binding constraint becomes Node.js's default — see N5 (ADVISORY-C001) below for the application-side complement.
- **Side effects and risks.** None of operational consequence at the c=1000 scale. The accept-queue memory footprint scales linearly with the cap but per-socket overhead is small (the queue holds connection-state structs, not connection data buffers). For comparison, a host with a few hundred MB of free RAM has plenty of headroom even at a backlog of 65 535. Recommendations to raise `somaxconn` to 4096 (or even higher) are standard practice on high-concurrency HTTP servers and are well-precedented in Linux kernel guidance.
- **Cross-reference.** [09-optimization-recommendations.md](./09-optimization-recommendations.md) R1.

### N2. Raise `net.ipv4.tcp_max_syn_backlog`

- **Tag**: **READY**
- **Symptom that triggers this recommendation.** Symptom 3 above — `dmesg` reports SYN flooding on port 3000 during a c=1000 run — fires even after N1 has been applied. This indicates that the constraint is not the listen-accept queue (which N1 has raised) but the upstream SYN backlog — the queue that holds half-open connections (i.e., connections for which the server has received a SYN and sent a SYN-ACK but has not yet received the final ACK of the three-way handshake).
- **Action — transient.** `sudo sysctl -w net.ipv4.tcp_max_syn_backlog=4096`.
- **Action — persistent.** Add `net.ipv4.tcp_max_syn_backlog = 4096` to `/etc/sysctl.d/99-backlog.conf` (the same file as N1 if applied together) and run `sudo sysctl --system`.
- **Action — verification.** `sysctl net.ipv4.tcp_max_syn_backlog` should report `4096`; the operator then re-runs c=1000 and confirms the SYN-flooding `dmesg` message no longer fires.
- **Effect.** Increases the size of the half-open connection table maintained by the kernel between SYN receipt and three-way handshake completion. Relevant in the harness's c=1000 rung because autocannon establishes 1000 connections in a burst at the start of each measured window, and the SYN-flood backlog is sized to hold the in-flight handshakes during that burst. With `tcp_max_syn_backlog` too small, the kernel applies SYN-cookies as a defense, which is functionally correct but is what triggers the `dmesg` message.
- **Side effects and risks.** Memory cost is minimal (each half-open entry is small). No correctness implication — SYN-cookies remain available as a fall-back if the backlog overflows even at 4096. Standard tuning for high-concurrency listeners; cited in the same Linux-kernel guidance that motivates N1.

### N3. Enable TCP Fast Open (optional)

- **Tag**: **READY (optional)**
- **Symptom that triggers this recommendation.** None specific to this report. TCP Fast Open is a latency optimization for clients that re-connect frequently to the same server; it allows the client's first data segment to be sent in the SYN packet, eliminating one round-trip of latency on subsequent connections. The benefit is dominated by network RTT, which is sub-100 µs on loopback per the "Loopback Round-Trip Baseline" section above, so the practical savings on this report's measurement substrate are negligible. The recommendation is documented for completeness because the same harness, run against a non-loopback deployment of an equivalent server, would benefit materially.
- **Action — transient.** `sudo sysctl -w net.ipv4.tcp_fastopen=3`. The value `3` enables TFO both as a client and as a server; `1` enables client only, `2` enables server only.
- **Action — persistent.** Add `net.ipv4.tcp_fastopen = 3` to `/etc/sysctl.d/99-backlog.conf` and re-apply.
- **Action — verification.** `sysctl net.ipv4.tcp_fastopen` should report `3`. TFO effectiveness is observable only by capturing packets with `tcpdump` and inspecting the SYN payload, which is outside the scope of this analysis.
- **Effect.** On loopback (this report's substrate), no measurable effect. On a real-network deployment that lifted the loopback binding at `[server.js:L3]` per the "Loopback vs. Real Network" discussion below, TFO would save one network round-trip per new connection that the client opens — typically a small fraction of a millisecond on a LAN, tens of milliseconds on a WAN.
- **Side effects and risks.** Some middleboxes (firewalls, load balancers) drop SYN packets carrying TFO data because their stateful packet inspection rules predate TFO; if the deployment includes such middleboxes the recommendation is best deferred until a packet-capture validation establishes that TFO SYNs traverse the path cleanly. On a loopback deployment there are no middleboxes, so this risk does not apply.

### N4. Raise per-process file-descriptor limit

- **Tag**: **READY**
- **Symptom that triggers this recommendation.** The c=1000 rung reports `errors` or `timeouts` accompanied by an `EMFILE` message in the server's stderr stream (which the harness archives at `benchmarks/results/<timestamp>/server.stderr.log`), and/or the harness's `[../../benchmarks/run-baseline.sh](../../benchmarks/run-baseline.sh)` pre-flight check emits the warning that the current `ulimit -n` is below 65535. This symptom is the primary topic of [06-event-loop-and-concurrency.md](./06-event-loop-and-concurrency.md) ("FD Pressure at c=1000"); it is restated here because the failure mode is intertwined with backlog saturation — both manifest as autocannon errors at c=1000, and the diagnostic disambiguates them.
- **Action — transient (per-shell).** Run `ulimit -n 65535` in the shell that will launch the harness, before invoking `[../../benchmarks/run-baseline.sh](../../benchmarks/run-baseline.sh)`. The new limit is inherited by child processes spawned from that shell, so both the server (`node ../server.js`) and the load generator (`autocannon`) will run with the elevated limit.
- **Action — persistent.** Add a stanza to `/etc/security/limits.d/99-nodejs.conf` of the form `* soft nofile 65535` and `* hard nofile 65535` (replace `*` with the operator's username for finer scoping). The change takes effect at the next login session; verify via `ulimit -n` in a fresh shell.
- **Action — verification.** `ulimit -n` should report `65535`. The harness's pre-flight check at `[../../benchmarks/run-baseline.sh](../../benchmarks/run-baseline.sh)` ("Pre-flight Checks") emits a warning if the value is below 65535; the warning should no longer appear after the limit is raised.
- **Effect.** At c=1000, each open TCP connection on the server occupies one file descriptor; with the default per-process limit of 1024 on many Linux distributions, the server is structurally incapable of handling 1000 concurrent connections without one or more `EMFILE` errors when the limit is approached (the server itself also uses a handful of FDs for stdin/stdout/stderr and the listening socket, reducing the effective ceiling further). Raising the limit to 65 535 removes this constraint by an order of magnitude beyond any rung the current ladder reaches.
- **Side effects and risks.** None at the harness's scale. Memory cost per FD is small. Standard practice for high-concurrency Node.js servers.
- **Cross-reference.** [06-event-loop-and-concurrency.md](./06-event-loop-and-concurrency.md) ("FD Pressure at c=1000") and [09-optimization-recommendations.md](./09-optimization-recommendations.md) R2.

## Application-Level Backlog Tuning (ADVISORY)

The single recommendation in this section is the application-side complement to N1 above. After N1 raises the kernel-level cap to 4096, the binding constraint on the effective backlog becomes Node.js's internal default — the value inferred to be 511 per the discussion in the "TCP Listen-Backlog" section above. To raise the effective backlog above 511, the application must request a higher value explicitly when it calls `server.listen()`. This necessarily modifies `[server.js:L12]`, which Constraint C-001 per `[README.md:L2]` and `[Section 2.6.2]` forbids without explicit owner approval.

### N5. Pass an explicit `backlog` argument to `server.listen`

- **Tag**: **ADVISORY-C001**
- **Symptom that triggers this recommendation.** N1 has been applied (kernel cap raised to 4096) and the c=1000 rung **still** exhibits backlog-related symptoms (any of Symptoms 1–3 in "Detecting Backlog Saturation" above). The diagnostic logic is: with the kernel cap at 4096 and the application default at the inferred 511, the binding constraint is now the application's default — so further mitigation requires raising the application's request.
- **Proposed source change.** Change `[server.js:L12]` from `server.listen(port, hostname, () => {...})` to the options-object form `server.listen({ port, host: hostname, backlog: 4096 }, () => {...})`. The options-object form is supported by the Node.js `net.Server.listen` API and accepts an explicit `backlog` field; the value `4096` aligns with the kernel cap raised by N1, so the effective backlog after both changes is the matched value 4096.
- **Constraint to relax.** Constraint C-001 per `[README.md:L2]` and `[Section 2.6.2]` — "Do not touch!" — is the binding constraint. Modifying `[server.js:L12]` requires the codebase owner to lift C-001 for this specific edit. The recommendation is therefore not applicable for an operator who must respect C-001; it is applicable only after the owner explicitly approves the source modification.
- **Effect.** Increases the application-side cap on the listen-accept queue from the inferred 511 to 4096, so that after both N1 and N5 are applied, the effective backlog reaches the kernel's new cap of 4096 (per the `min(backlog_argument, somaxconn)` rule in the "TCP Listen-Backlog" section above). At that point the c=1000 rung no longer saturates the backlog and any residual c=1000 symptoms must be attributable to the event-loop saturation analyzed in [06-event-loop-and-concurrency.md](./06-event-loop-and-concurrency.md) or to the file-descriptor pressure addressed by N4 — the kernel and application no longer constrain the connection-arrival rate.
- **Alternatives considered.** A larger backlog argument (e.g., `backlog: 8192`) would shift the application cap further above the kernel cap, making the kernel cap the binding constraint and rendering N1 the relevant tuning lever; the matched value 4096 is preferred because it makes the two caps coincide, which is the simplest configuration to reason about. A smaller backlog argument is not motivated by any symptom in this report.
- **Cross-reference.** This chapter's **N5** is aggregated in [09-optimization-recommendations.md](./09-optimization-recommendations.md) as **A1-5** under the ADVISORY-C001 cluster ("Pass an explicit backlog argument to `server.listen`"). The pairing with N1 is also reflected in chapter 09's discussion of the kernel/application backlog `min()` relationship — N1 is aggregated as **R1** under the READY cluster, and the two entries cross-reference each other to make explicit that R1 alone is the only READY half of the pair. N5/A1-5 should be considered only after R1/N1 has been applied and the c=1000 symptom persists; this priority ordering is preserved in chapter 09's aggregation.

## Loopback vs. Real Network

Every latency number reported in this analysis — at every concurrency rung, every percentile, every chapter — is a loopback latency number. Loopback measurement does not reflect production latency for any deployment that exposes the server beyond the local host. Real network latency adds a contribution that varies by deployment scale: tens of microseconds for a same-host container-to-container path traversing a bridge interface, hundreds of microseconds to a few milliseconds for a same-datacenter LAN path, tens to hundreds of milliseconds for a wide-area path between regions, and beyond a hundred milliseconds for intercontinental paths. For any deployment that placed the server behind a public IP, the network latency contribution would dominate the per-request handler cost by orders of magnitude — a 50-millisecond WAN RTT is approximately 250× larger than the sub-200-µs loopback RTT this chapter documents — and the conclusions reached in this report about where latency is spent would invert: at WAN scale, latency is dominated by the network, not by the handler at `[server.js:L6-L10]` and not by the event loop documented in [06-event-loop-and-concurrency.md](./06-event-loop-and-concurrency.md). The optimization recommendations would correspondingly invert as well: network-level optimizations (keep-alive reuse, TFO per N3 above, CDN placement, HTTP/2 multiplexing) would dominate the value table, while CPU-level handler optimizations would become essentially irrelevant.

Lifting the loopback binding — that is, changing `[server.js:L3]` from `'127.0.0.1'` to `'0.0.0.0'` or to a specific non-loopback interface address — is ADR-003 territory per `[Section 6.5.7]` and requires relaxing two constraints simultaneously: Constraint C-001 per `[Section 2.6.2]` (because the literal at `[server.js:L3]` would be modified) and Constraint C-004 per `[Section 2.6.2]` (because exposing the server beyond loopback is part of the hardcoded-configuration boundary that C-004 protects). Such a change would also entail a security review per `[Section 2.4.4]` because the application currently exposes zero attack surface beyond the loopback adapter and any bind-address widening fundamentally alters that posture. None of those changes are recommended by this report; the loopback binding is documented as a structural choice of the system whose performance implications this chapter records, not as a defect to be remediated.

The reader who is consuming this report in preparation for a deployment that *would* lift the loopback binding should treat every latency number in every chapter as a **lower bound** rather than a production estimate. A future revision of the harness that ran against a non-loopback address would produce a different, larger number for every latency cell; the qualitative shape of the curves (near-linear RPS growth to a saturation knee, p99 tail expansion at high concurrency) would be preserved but the absolute numbers would shift upward by the network-latency contribution. This chapter's numbers are therefore the floor of what the system can achieve, not the ceiling and not the operating point of any real deployment.

## Summary

The table below restates the five recommendations introduced in this chapter, their tags, and the symptom each addresses. The READY recommendations (N1 through N4) are applicable immediately by an operator with host-level administrative privileges and require no relaxation of Constraints C-001 through C-004 per `[Section 2.6.2]`. The single ADVISORY recommendation (N5) requires the codebase owner to relax Constraint C-001 — that is, to approve an edit to `[server.js:L12]` — before it can be applied.

| ID | Recommendation | Tag | Effect |
|----|----------------|-----|--------|
| N1 | Raise `net.core.somaxconn` to 4096 | READY | Increases kernel cap on listen-accept queue; resolves backlog-driven SYN drops at c=1000 |
| N2 | Raise `net.ipv4.tcp_max_syn_backlog` to 4096 | READY | Enlarges half-open connection table; resolves SYN-flood `dmesg` warnings at c=1000 |
| N3 | Enable TCP Fast Open (`net.ipv4.tcp_fastopen=3`) | READY (optional) | Minor latency saving on non-loopback deployments; no measurable effect on loopback |
| N4 | Raise per-process FD limit (`ulimit -n 65535`) | READY | Avoids `EMFILE` at c=1000; complements [06-event-loop-and-concurrency.md](./06-event-loop-and-concurrency.md) "FD Pressure at c=1000" |
| N5 | Pass `backlog: 4096` explicitly to `server.listen` at `[server.js:L12]` | ADVISORY-C001 | Aligns application-side cap with kernel cap after N1 is applied; requires C-001 relaxation |

The single highest-impact recommendation in this chapter is **N1** — raising `net.core.somaxconn` to 4096 — because it is the kernel cap that binds at c=1000 on hosts whose distribution default is 128, it is external to the application (no source change), and it addresses the most likely saturation symptom that the c=1000 rung exhibits. A future extension of `[../../benchmarks/run-baseline.sh](../../benchmarks/run-baseline.sh)` (itself a READY-tagged recommendation tracked at [09-optimization-recommendations.md](./09-optimization-recommendations.md) as **R11** — "Add a `net.core.somaxconn` / FD-limit pre-flight check and a `ss -ltn Recv-Q` passive sampler to the harness") could be the pre-flight check at the harness level: read `net.core.somaxconn`, compare against the c=1000 rung's connection count, and emit a warning if the current value is below 4096; the same harness extension can also sample `ss -ltn` periodically to observe `Recv-Q` (the kernel's current backlog depth on the listening socket) during the run, closing the observability gap between symptom and remediation without requiring application-level changes. **R11** (the harness pre-flight / sampler) is distinct from **R1** (the kernel tuning value itself): R1 says "set `somaxconn` to 4096"; R11 says "make the harness *check* what `somaxconn` is and warn when it is too low".
