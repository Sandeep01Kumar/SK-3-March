# Event Loop and Concurrency

Per `[Section 5.2.1]`, Node.js runs JavaScript on a single thread — the **event loop** — and every request handler dispatch, every callback execution, and every timer firing happens on that one thread. **Event-loop lag** is the wall-clock time between when a callback is scheduled to run and when it actually runs; it is therefore the *primary* indicator of CPU and scheduling pressure on a Node.js process. When the event loop is healthy, lag is near the noise floor (single-digit microseconds). When the event loop is saturated, lag grows superlinearly with concurrency and propagates directly into perceived HTTP latency, because every queued request waits behind every other queued callback. This chapter analyzes lag and concurrent-connection behavior for the bare HTTP serving path of `[server.js:L1-L14]` using the CSV stream emitted by `[../../benchmarks/measure-event-loop-lag.sh](../../benchmarks/measure-event-loop-lag.sh)` (written to `benchmarks/results/<timestamp>/event-loop-lag.csv`) and the autocannon JSON written from the same run (`benchmarks/results/<timestamp>/autocannon-during-elag.json`). Per the design note documented at the top of `[../../benchmarks/measure-event-loop-lag.sh](../../benchmarks/measure-event-loop-lag.sh)`, the sampler is a **separate Node helper process** that measures **its own** event loop via `perf_hooks.monitorEventLoopDelay()` and `performance.eventLoopUtilization()`; it cannot directly observe the server's event loop without violating Constraint C-001 (which forbids modifying `server.js`). To compensate, the same sampler issues an HTTP probe against `http://127.0.0.1:3000/` at every interval and records the **probe RTT** — and the probe RTT is the more direct, server-side signal because every probe response is gated on a tick of the server's event loop. The two columns serve complementary roles and reviewers must not conflate them; the methodology caveat is restated in every per-rung interpretation below.

## CSV Format

The harness emits one CSV per invocation under `benchmarks/results/<timestamp>/event-loop-lag.csv` (one row per sample interval). The CSV header is documented in the harness source at `[../../benchmarks/measure-event-loop-lag.sh](../../benchmarks/measure-event-loop-lag.sh)` ("CSV Schema") and is also encoded as a literal string written by the sampler `mjs` helper that the parent shell script generates into the same results directory. The header is:

```
epoch_ms,interval_ms,elu_pct,lag_min_ns,lag_mean_ns,lag_p50_ns,lag_p99_ns,lag_max_ns,probe_rtt_ms,probe_status
```

Per-column semantics (mirroring the harness's in-source documentation so that the chapter and the harness cannot drift):

- **`epoch_ms`** — sample timestamp in epoch milliseconds, captured at the top of each helper tick. Rows are **not** strictly monotonic in write-order because probes complete in parallel with the next tick's sample; consumers MUST sort by `epoch_ms` before any time-series aggregation. The methodology caveat is encoded directly in the harness's comments at the schema section of `[../../benchmarks/measure-event-loop-lag.sh](../../benchmarks/measure-event-loop-lag.sh)`.
- **`interval_ms`** — the nominal sample interval, equal to the harness's `SAMPLE_INTERVAL_MS` constant (default 200 ms — five samples per second). The actual wall-clock window between samples may differ slightly under scheduler jitter; downstream aggregation that needs the realized interval should compute it from successive `epoch_ms` deltas rather than relying on this field.
- **`elu_pct`** — event-loop utilization of the **helper sampler process**, in percent, since the previous tick. Computed from `performance.eventLoopUtilization()` deltas. Reflects how much wall-clock time the sampler's loop spent on synchronous work between ticks; high values indicate the sampler itself is under load (which can happen if probes are slow or many resolve in the same tick), not necessarily that the server is under load.
- **`lag_min_ns`, `lag_mean_ns`, `lag_p50_ns`, `lag_p99_ns`, `lag_max_ns`** — histogram statistics of event-loop delay for the **sampler's own loop**, in nanoseconds, computed from `perf_hooks.monitorEventLoopDelay()` and read out at the end of each interval. These columns are the sampler's lag, **not** the server's; their utility for server-side load assessment is indirect — they correlate with server lag only insofar as both processes share CPU on the same host, so under sustained whole-host load they will tend to rise together.
- **`probe_rtt_ms`** — round-trip time of an HTTP GET against `http://127.0.0.1:3000/`, in milliseconds. This is the **server-side** signal: every probe completes a full request-response cycle through the server's event loop, so a slow probe directly reflects server-side handler-tick contention or kernel-level accept-queue queueing. This is the primary column when reasoning about server load.
- **`probe_status`** — the HTTP status code from the probe (`200` expected from `[server.js:L7]`; `0` if the probe errored, timed out, or its socket was reset). Any value other than `200` is operationally significant: it indicates the server failed to respond cleanly within the interval, typically because the host is under such load that even a single-connection probe is queueing.

The reader who wants the raw evidence — for example, to verify a number cited later in this chapter — opens the CSV from the most recent `benchmarks/results/<timestamp>/` directory, sorts by `epoch_ms`, and applies the per-rung filtering described next. Per the validation step in this chapter's agent prompt and the harness's "CSV Schema" comment block, this 10-column header is **canonical**; any divergence between the documented header above and the actual first line of `event-loop-lag.csv` is a harness bug, not a chapter bug, and should be reported against the harness.

### c=1 (one persistent connection)

At c=1, the sampler's lag p50 is expected to sit at the noise floor — typically below 1 µs on a modern Linux kernel with no other CPU pressure on the host. The sampler's loop has nothing to do between ticks except wait for `setInterval` to fire, so the histogram observed at the end of each interval reflects scheduler jitter only. Probe RTT p50 is dominated by loopback transport: a localhost TCP connect on `127.0.0.1` per `[server.js:L3]` followed by request line parsing, the handler's three statements at `[server.js:L7-L9]` (status assignment, header set, body write), and response framing back across the loopback adapter. On modern Linux, end-to-end loopback HTTP probe latency is typically sub-millisecond; a materially higher c=1 probe RTT would indicate non-trivial handler-side work — which is surprising given that `[server.js:L6-L10]` contains no I/O, no regex, no JSON parse, no allocation of consequence beyond the per-request `IncomingMessage` and `ServerResponse` objects discussed in [04-cpu-and-memory-profile.md](./04-cpu-and-memory-profile.md) ("Heap Profile"). ELU at c=1 is expected to be near zero for the sampler — the sampler does almost no work, because the single in-flight probe completes long before the next 200 ms tick.

### c=10 (ten parallel connections)

At c=10, the lag and probe-RTT statistics typically remain close to the c=1 floor because concurrency at this level does not saturate any resource on the host. Ten parallel connections interleave on the single-threaded event loop without meaningfully queueing — each handler tick processes a request in microseconds (per `[Section 5.2.1]`'s description of the single-threaded execution model), and the event loop has ample headroom to dispatch each connection's pending request before the next one arrives. The sampler's lag p99 may rise modestly relative to c=1 because the host's TCP stack is now serving ten concurrent connections instead of one, and the sampler's probe is competing with autocannon's traffic for socket-buffer time. Probe RTT p99 may show a small but measurable spread relative to p50, reflecting the slight non-determinism introduced by ten interleaving connection-state machines.

### c=100 (one hundred parallel connections — harness default)

c=100 is the harness's *default* (`LOAD_CONNECTIONS=100`) and is therefore the rung the operator most commonly inspects when running the script without modification. At this rung, the sampler's lag p99 typically begins to spread relative to p50 if the per-tick handler dispatch cost approaches the loop's iteration budget — that is, if many requests arrive within the same tick boundary, the loop processes them serially and the last few requests in the batch wait. Probe RTT p99 may begin to climb materially relative to p50 at this rung for the same reason: a probe that arrives at the end of a busy tick waits behind 99 other in-flight requests. ELU for the sampler is expected to remain modest (well below 50%) because the sampler still has only one probe in flight at a time; the sampler's lag column is therefore not the right signal at this rung — probe RTT is.

### c=1000 (one thousand parallel connections — saturation candidate)

c=1000 is the rung that the load profile explicitly designates as the **saturation candidate** (see `[../../benchmarks/load-profile.json](../../benchmarks/load-profile.json)`'s `scenarios[3].notes`: "high concurrency; tests TCP listen-backlog (default 511 per node http.Server) and FD limits"). At this rung, multiple resource limits intersect simultaneously: the kernel's listen-backlog (default 511 — see [07-network-latency.md](./07-network-latency.md), "TCP Listen-Backlog"), the process's open-file-descriptor limit (typically 1024 by default on Linux — see "FD Pressure at c=1000" below), and the single-threaded event loop's per-iteration budget. The expected signature is: lag p99 spikes superlinearly relative to c=100, probe RTT p99 spikes in correlation with sampler lag (and at higher absolute values because the probe must traverse the server's event loop, not just the sampler's), ELU approaches or saturates at 100%, and `autocannon-during-elag.json` reports either reduced RPS, increased non-2xx counts, or non-zero socket errors. If **all four** signals are present, the application is event-loop-bound at c=1000. If only some signals are present, the bottleneck may be elsewhere (most commonly the FD limit or the listen-backlog — see the dedicated sections below).

## Backlog Saturation

A new TCP connection arriving at a Node.js HTTP server transits two queues before its first byte reaches the application: the **kernel SYN queue** (sized by `net.ipv4.tcp_max_syn_backlog`) and the **listen-accept queue** (the smaller of `net.core.somaxconn` and the `backlog` argument passed to `listen()`). Node.js's `[server.js:L12]` invokes `server.listen(port, hostname, callback)` **without** an explicit backlog argument; Node.js's default is **511** per the `http.Server` documentation — the practical interpretation of which is detailed in [07-network-latency.md](./07-network-latency.md) ("TCP Listen-Backlog and `net.core.somaxconn`"). When new SYNs arrive faster than the application can drain the accept queue, the kernel begins to **drop** SYNs (or, with `tcp_abort_on_overflow=1`, sends RST), and the load generator records the casualties.

The harness observes backlog saturation indirectly through `benchmarks/results/<timestamp>/autocannon-during-elag.json`. The relevant autocannon JSON fields are `errors`, `timeouts`, and `non2xx` (counts of socket errors, request timeouts, and non-2xx responses respectively). For the static handler at `[server.js:L6-L10]`, there is no application-level failure mode that produces non-2xx responses — `[server.js:L7]` unconditionally sets `res.statusCode = 200`, and the response body at `[server.js:L9]` is a 14-byte compile-time constant. Therefore, **any** non-zero value in `errors`, `timeouts`, or `non2xx` at c=1000 is, by elimination, evidence of TCP-layer or kernel-layer saturation rather than application-layer failure. The chapter's interpretation rule is explicit:

- `errors > 0` or `timeouts > 0` at c=1000 → backlog or FD saturation evidence; cross-reference [07-network-latency.md](./07-network-latency.md) ("TCP Listen-Backlog") and "FD Pressure at c=1000" below.
- `non2xx > 0` at c=1000 → cannot occur from `[server.js:L6-L10]` alone (the handler always writes 200), so any non-zero value indicates the response was dropped before reaching the handler (typically a connection reset mid-request); this is also backlog or kernel-layer evidence.
- All three at zero at c=1000 → backlog saturation has **not** occurred at this rung; the bottleneck (if any) is elsewhere (event-loop dispatch cost, host CPU, or simply: the host has not yet been pushed past saturation by a four-rung ladder and the agent should extend the ladder per R3 in [09-optimization-recommendations.md](./09-optimization-recommendations.md)).

The c=1000 measurements from `autocannon-during-elag.json` should be recorded here once captured: `errors=<TBD on first run>`, `timeouts=<TBD on first run>`, `non2xx=<TBD on first run>`. The implementing agent reads these from the JSON's top-level counters (the autocannon schema; consult the manifest at `event-loop-lag-manifest.json` for the exact autocannon major version, since field naming is version-dependent across autocannon majors).

## Head-of-Line Blocking

HTTP/1.1 supports two distinct concurrency models, and the two are routinely confused in performance writing: **parallel connections** (the load generator opens N TCP connections and issues one request at a time on each) and **pipelining** (the load generator opens fewer connections but issues multiple requests back-to-back on each connection without waiting for responses). Autocannon's default behavior at high `-c` is **parallel connections, not pipelining**; pipelining requires the explicit `--pipelining N` flag. The harness's autocannon invocation at `[../../benchmarks/measure-event-loop-lag.sh](../../benchmarks/measure-event-loop-lag.sh)` (line 449–452) passes `-c "$LOAD_CONNECTIONS"` and `-d "$LOAD_DURATION"` and `-j "$URL"` only — no `--pipelining` — so the chapter's discussion below assumes parallel connections.

Under parallel connections, head-of-line blocking is only relevant **per connection**, and on a per-connection basis the static handler at `[server.js:L6-L10]` finishes each request synchronously in microseconds (the three statements at `[server.js:L7-L9]` are non-blocking — they touch the response object's internal buffers without performing I/O). Therefore, on a single TCP connection, no request can meaningfully head-of-line-block any other request: the response is written and the next request is parsed before any noticeable wall-clock time elapses. Across the *N* parallel connections, each connection's request queue is independent at the protocol level; head-of-line blocking across connections happens at the *kernel-scheduling* layer, not at the HTTP layer.

Under pipelining (which the harness does **not** exercise by default but which is observable if `--pipelining N` is added to the autocannon invocation), responses are still written in request-receive order per the HTTP/1.1 spec. For this server, since every response is byte-identical (the same 14-byte body at `[server.js:L9]`, the same `Content-Type: text/plain` header at `[server.js:L8]`, the same `200` status at `[server.js:L7]`), pipelining produces no head-of-line blocking benefit *or* penalty: the responses' wire footprints are identical, so no fast response is held up behind a slow one and no slow response benefits from being batched. For workloads where responses vary in size or computation cost, pipelining can have material effects; for this workload, **pipelining versus parallel connections has minimal effect on per-request latency**, and the chapter's measurements taken under autocannon defaults are representative.

## Event-Loop Saturation Signature

A Node.js HTTP server saturated at the event-loop layer (as opposed to the network layer or the FD layer) exhibits a **characteristic four-signal signature** in the harness output:

1. **Sampler lag p99 grows superlinearly with concurrency.** Because the sampler shares the host with the server, lag in the sampler's own loop is a host-level CPU-pressure proxy. At low concurrency, lag p99 sits at the noise floor; at the saturation rung, lag p99 rises sharply — typically by a factor of 10× to 100× relative to the next-lower rung.
2. **Probe RTT grows in correlation with sampler lag.** Because every probe traverses the server's event loop, probe RTT is the direct server-side signal. At the saturation rung, probe RTT p99 is materially larger than at the next-lower rung; the ratio between probe RTT p99 and probe RTT p50 widens.
3. **ELU approaches 100%.** Sampler ELU is expected to remain modest at all rungs (the sampler's work is bounded), but **server-side ELU**, if it could be observed (it cannot, per Constraint C-001), would approach 100% at the saturation rung. The harness's interpretation rule is that when sampler ELU climbs materially above the c=1 baseline at high concurrency, the *host* is under pressure — which strongly implies the server (the host's main consumer) is too.
4. **Autocannon throughput plateaus or declines.** `autocannon-during-elag.json` reports `requests.average` (RPS) and `latency` (percentile histogram). At saturation, RPS either plateaus relative to the next-lower rung or actively declines while latency rises — the classic "queueing" signature.

**Interpretation rule.** If all four signals are present at c=1000, the application is **event-loop-bound** at c=1000 — the dominant bottleneck is dispatch cost inside the single-threaded JavaScript event loop, not the kernel, not the network, not the FD limit. If only some signals are present (for example, sampler lag and probe RTT spike but ELU does not, or autocannon throughput plateaus but lag and probe RTT do not), the bottleneck is elsewhere and the chapter records the specific subset of signals observed so that the diagnosis can be refined. The most common alternative bottlenecks at c=1000 on a host with adequate CPU are: the FD limit ("FD Pressure at c=1000" below), the listen-backlog ([07-network-latency.md](./07-network-latency.md)), or kernel-side per-connection state (which manifests as elevated probe RTT without elevated sampler lag, because the kernel is queueing but the JavaScript loop is idle).

A particularly diagnostic combination is **elevated probe RTT with low sampler lag at c=1000**: this is the signature of *server-only* pressure that does not affect the sampler. It indicates that the server is bottlenecked specifically by HTTP-layer work (parser, header writer, response framer at `[server.js:L7-L9]`) while the rest of the host is idle. The opposite combination — **elevated sampler lag with low probe RTT** — would indicate that the host itself is under pressure from some non-server source (the sampler, autocannon, or the kernel under high concurrency) but the server's individual work per request remains cheap, so probes finish quickly even though the host is busy.

## Concurrent-Connection Behavior

The harness opens `c` long-lived TCP connections to `http://127.0.0.1:3000/` (autocannon's default keep-alive behavior; the harness does not pass `--no-keepalive`). Each connection sustains a request-response loop for `LOAD_DURATION` seconds. With default settings (no `--pipelining`), at most one request is in flight per connection at a time; the total number of concurrent in-flight requests on the server is therefore bounded by `c` (or `c × pipelining` if pipelining is enabled, which it is not by default).

Server-side per-connection overhead is fully characterized by `[server.js:L1-L14]` and `[Section 5.2.1]` (single-threaded event loop). For each connection:

- **Accept callback** — one libuv-level `on('connection')` invocation per TCP accept. Allocates an internal `Socket` object.
- **Parser invocation** — one HTTP parser invocation per request, which extracts the request line and headers from the bytes received on the socket. Node.js maintains parser state per-connection so that pipelined requests can be processed without re-allocating.
- **Handler dispatch** — one synchronous call into the function defined at `[server.js:L6-L10]` per request. Executes three statements (`res.statusCode = 200`, `res.setHeader('Content-Type', 'text/plain')`, `res.end('Hello, World!\n')`) and returns.
- **Response write** — the bytes emitted by `res.end()` at `[server.js:L9]` are framed into an HTTP/1.1 response and written to the socket; with keep-alive enabled (autocannon's default), the connection remains open and the next request begins.

There is **no per-connection state** beyond what Node.js and libuv allocate internally: no session, no cookie store, no per-connection user identity, no in-memory cache keyed by connection — none of these exist in `[server.js:L1-L14]` because, per `[Section 5.1.3]`, "No data from the incoming request — method, path, headers, or body — is read, evaluated, or stored." The server is fully **stateless** at the application layer.

The per-connection memory footprint is therefore dominated by Node.js's internal `Socket` object plus libuv's per-FD bookkeeping plus the per-connection HTTP parser state. A typical figure for an idle keep-alive HTTP/1.1 connection in Node.js is **on the order of 10 KB per connection** (Socket buffers, parser state, internal arrays); at the c=1000 rung, this is approximately **`1000 × ~10 KB = ~10 MB`** of incremental RSS attributable to connection state. The implementing agent should cross-validate this ballpark against the RSS samples recorded in [04-cpu-and-memory-profile.md](./04-cpu-and-memory-profile.md) ("RSS Sampling") — specifically, the delta between the c=1 RSS baseline and the c=1000 RSS peak should be in the single-digit-to-low-double-digit MB range; a materially larger delta would indicate per-connection state growth that the application code does not produce and that would therefore be a Node.js or libuv-version artifact worth recording.

## FD Pressure at c=1000

Every accepted TCP connection consumes one **file descriptor** on the server process. Additionally, the server holds open descriptors for `stdin`, `stdout`, `stderr`, the listening socket itself, and any logs (in this case only `console.log` at `[server.js:L13]` to stdout, which does not open a separate FD). At the c=1000 rung, the server needs at least **1004 descriptors** (1000 accepted connections plus 4 baseline) to avoid `EMFILE` (errno: "too many open files"). The Linux default soft `ulimit -n` is typically **1024**, which is **insufficient** — even setting aside the baseline 4 descriptors, the kernel will refuse the `accept()` of the 1021st or later connection with `EMFILE` and the server will log the error to stderr.

The harness mitigates this risk with a **pre-flight warning** issued by `[../../benchmarks/run-baseline.sh](../../benchmarks/run-baseline.sh)`: if the current shell's `ulimit -n` is below 4096, the harness logs a warning and recommends raising the limit before launching the c=1000 scenario. (The `measure-event-loop-lag.sh` script defers to the operator on this point — it does not itself re-issue the warning, because by design it runs at one concurrency level per invocation and the operator running it at c=1000 is expected to have already heeded `run-baseline.sh`'s warning during the regular baseline campaign.) The operational instruction is simple: **run `ulimit -n 65535` in the shell before invoking the harness at c=1000**, or equivalently configure the system-wide `/etc/security/limits.conf` so that the soft limit is raised for the user running the benchmark.

If the harness is run at c=1000 with the default `ulimit -n 1024`, the chapter's interpretation reads as follows. The `autocannon-during-elag.json` file will likely show non-zero `errors` (socket-level: the kernel refused the `accept()` so autocannon's `connect()` got `ECONNREFUSED` or the listening socket's accept queue overflowed) and possibly non-zero `non2xx` (autocannon may count a connection-reset mid-request as a non-success even if no HTTP status code was actually received). The server's `stderr.log` (captured by the harness at `$RESULTS_DIR/server.stderr.log` per the harness's "Outputs" comment block) will show `EMFILE` events. The harness's "FD pressure" diagnosis is **decisive** when both signals are present: autocannon errors + server EMFILE messages = FD saturation, period. Recommended remediation is to raise `ulimit -n` and re-run; this is recommendation **R2** in this chapter's "Recommendations" table below and in [09-optimization-recommendations.md](./09-optimization-recommendations.md) ("READY recommendations").

## Workflow Gap Note

Workflows that would normally introduce concurrency pressure beyond bare HTTP serving — long-running authentication flows that hold a request open while validating tokens or hitting an identity provider, large file uploads that consume bytes from the request body over many event-loop ticks, slow database queries that block on disk or network I/O, third-party integration calls that wait on outbound HTTP — **do not exist** in this codebase per [02-workflow-gap-analysis.md](./02-workflow-gap-analysis.md). Seven of eight workflow categories named in the user's prompt are recorded ABSENT in that chapter; the one PRESENT workflow is the static HTTP endpoint at `[server.js:L6-L10]`. The event-loop pressure measured in this chapter therefore reflects **purely the bare HTTP serving path** — request parser cost, response framer cost, socket-write cost — and does not include any of the workflow-shaped pressures that would dominate a real-world application's saturation profile. Readers comparing these numbers to a production Node.js HTTP server should adjust their expectations accordingly: the saturation point measured here is an upper bound on what `[server.js:L1-L14]` can sustain, and a real application built on the same Node.js runtime version would saturate at a *lower* concurrency because of the additional per-request work that this application omits.

## Recommendations

The recommendations below are organized into READY items (no codebase constraint must be relaxed; the operator can apply them immediately) and ADVISORY items (the corresponding constraint from AAP §0.7 must be lifted before the recommendation can be applied). Each recommendation cross-references the chapter where it is explored in greater depth; this chapter's table is a summary of items most directly motivated by the event-loop and concurrency findings.

| ID | Recommendation | Tag | Effect |
|----|----------------|-----|--------|
| R2 | Run `ulimit -n 65535` before invoking the harness at c=1000 | READY | Avoids `EMFILE` on the 1024th accepted connection at the c=1000 rung; eliminates the most common spurious "saturation" finding |
| R1 (chapter 07) | Raise `net.core.somaxconn` to at least 1024 (or higher) to match the harness's c=1000 rung | READY | Avoids kernel-level accept-queue truncation; ensures the listen-backlog is not the bottleneck obscuring the true saturation point |
| A1-3 (chapter 09) | Adopt Node.js's `cluster` module to fork one server process per CPU core | ADVISORY-C001 | Multiplies effective throughput by the core count; removes the single-threaded event loop as the sole dispatch path |
| A1-4 (chapter 09) | Introduce a reverse proxy (nginx, HAProxy) in front of multiple Node.js instances | ADVISORY-C001, ADVISORY-C003 | Decouples connection-acceptance from request-dispatch; absorbs concurrent connection spikes at the proxy layer |

R2 is the highest-impact READY recommendation because it eliminates the most common confounding signal at the c=1000 rung: an `EMFILE`-bound run looks superficially like an event-loop-saturation run (both produce elevated probe RTT and non-zero autocannon errors), but the remediation is completely different. R1 (cross-referenced from [07-network-latency.md](./07-network-latency.md)) is the second-highest-impact READY recommendation because it eliminates the kernel-layer accept-queue limit; together with R2, R2+R1 ensure that c=1000 measurements reflect actual event-loop behavior rather than environmental artifacts. The two ADVISORY recommendations (cluster and reverse-proxy) are the architectural answers to event-loop saturation — they are the only path to scaling beyond what a single event loop can dispatch — but both require lifting Constraint C-001 (the "Do not touch!" governance directive at `[../../README.md:L2]` and AAP §0.7); they are therefore tagged ADVISORY and deferred to [09-optimization-recommendations.md](./09-optimization-recommendations.md) for owner review. The reverse-proxy recommendation additionally implicates Constraint C-003 (single-purpose server) because it introduces a multi-component architecture; the tagging reflects that dependency.
