# Observability Recommendations

The application's observability surface consists of exactly one emission: the `console.log` invocation at `[server.js:L13]` that prints the startup string `Server running at http://${hostname}:${port}/` to standard output a single time per process lifecycle, after `server.listen(port, hostname, callback)` at `[server.js:L12]` reports successful binding. Beyond that single startup line, the running process emits no per-request log entries, no metrics in any format (no counters, no histograms, no gauges), no distributed-tracing spans, no health-probe endpoint, and no periodic resource-usage snapshots — a posture that is confirmed by `[Section 6.5]` ("Monitoring and Observability") and recorded explicitly in `[Section 6.5.2]` ("Observability evidence: one `console.log` only"). The structural reason for this absence is not oversight: every standard observability lever — HTTP access logging, application logging via a structured logger, Prometheus-style `/metrics` exposition, OpenTelemetry trace context propagation, a `/health` endpoint distinct from the production route — would require modifying `[server.js:L1-L14]`, which is prohibited by Constraint C-001 ("Do not touch!") per `[README.md:L2]` and `[Section 2.6.2]`; most of them would additionally require adding a dependency to `[package.json:L1-L11]`, which is prohibited by Constraint C-002 ("Zero external dependencies") per `[Section 2.6.2]` and is empirically verifiable from the empty `packages` map at `[package-lock.json:L6-L11]`; and the metrics endpoint specifically would require introducing a URL branch into the handler at `[server.js:L6-L10]`, which is prohibited by Constraint C-003 ("Single-purpose") per `[Section 2.6.2]`. Every recommendation in this chapter is therefore **ADVISORY** rather than READY; no observability change can be applied without prior owner approval to lift the corresponding constraint or constraints, and the cross-referenced summary in [09-optimization-recommendations.md](./09-optimization-recommendations.md) groups each recommendation under its applicable tag section. For the canonical record of which workflows are PRESENT and ABSENT in the codebase — the broader context that explains why most observability targets (auth flows, dashboard, file I/O, third-party integrations, database queries, frontend rendering, background jobs) have nothing to instrument in the first place — the chapter defers to [02-workflow-gap-analysis.md](./02-workflow-gap-analysis.md).

## Current Observability Surface

The five categories of runtime telemetry that production Node.js HTTP applications commonly emit are enumerated below alongside the count of emissions presently produced by `[server.js:L1-L14]`. Each row is independently verifiable from the source: the implementing agent can confirm every count by reading the 14 lines and observing what is and is not present in them.

- **Logging — 1 emission, at startup, plain string.** The single `console.log` at `[server.js:L13]` runs once when the server's listen callback fires and emits the literal template-string `` `Server running at http://${hostname}:${port}/` ``. This is a startup-confirmation signal, not a runtime observability signal. There is no per-request log entry, no error log, no shutdown log, and no log rotation, formatting, level filtering, or destination redirection. The output goes to whichever file descriptor the operator's invocation has wired to standard output (a terminal in foreground mode, the supervisor's log capture in daemonized mode); there is no internal buffering, sampling, or back-pressure mechanism.
- **Metrics — 0 metrics.** No counters (e.g., `http_requests_total`), no histograms (e.g., `http_request_duration_seconds`), no gauges (e.g., `nodejs_eventloop_lag_seconds`, `process_resident_memory_bytes`), and no summaries. The application imports neither `prom-client` (per `[package.json:L1-L11]` and `[package-lock.json:L6-L11]` — both confirm zero dependencies) nor any custom metrics primitive. There is no `/metrics` route to scrape; an HTTP `GET /metrics` against `127.0.0.1:3000` returns the same `200 OK` with body `'Hello, World!\n'` as `GET /` does, because the handler at `[server.js:L6-L10]` does not inspect `req.url`.
- **Traces — 0 spans.** No distributed-tracing context is created on inbound requests, none is propagated to downstream calls (there are no downstream calls per `[Section 3.4.1]` and `[Section 5.1.4]`, so this is doubly absent), and no exporter is registered. No OpenTelemetry SDK, no Zipkin client, no Jaeger client, and no proprietary APM agent (New Relic, Datadog, Elastic APM) is present in the dependency graph.
- **Health endpoint — None.** There is no path-based health probe. `GET /health` returns the same `200 OK` and the same `'Hello, World!\n'` body as `GET /`, because the handler does not branch on the URL — confirmed by the absence of any `if (req.url === ...)` construct in `[server.js:L6-L10]` and by the broader observation in `[Section 5.1.3]` that "no data from the incoming request — method, path, headers, or body — is read, evaluated, or stored." A load balancer or orchestrator that requires a distinct health-probe path cannot distinguish a healthy server from an unhealthy one beyond observing that the TCP listener accepts connections.
- **Process telemetry — None.** There is no periodic emission of `process.memoryUsage()` (RSS, heap-used, heap-total, external, array-buffers), no emission of `process.cpuUsage()` deltas, and no event-loop lag sampling (which would require either the `perf_hooks` built-in's `monitorEventLoopDelay` API or a `setImmediate`-based heuristic). The process emits its startup line at `[server.js:L13]` and is then silent until an operator terminates it with SIGINT or until the process crashes.

The operational consequence of this posture is that an operator cannot detect that the server is in a degraded state from inside the process — there is no signal the server itself emits that would distinguish a healthy steady state from a near-saturation state, from a memory-leak state, from an event-loop-blocked state, or from a process-crashed state. Failures are visible only **externally**: the client receives no response or a connection-refused error, an external monitoring system observes that TCP probes against `127.0.0.1:3000` fail, or an operator notices that the foreground `node server.js` process is no longer running in the terminal session that launched it. By contrast, every recommendation in this chapter aims to surface at least one observability signal that an operator or downstream system can consume — request attribution (O1), quantitative time-series scraping (O2), trace-context propagation (O3), full commercial-APM telemetry including transactions / errors / infrastructure metrics (O4), or on-demand process-level snapshots driven by an external signal (O5). The constraint-relaxation cost of each varies considerably, and the Summary table at the end of this chapter is the canonical side-by-side comparison; reviewers choosing where to begin are encouraged to start with the smallest-footprint option that yields the observability they most need. Two related but distinct patterns — a `GET /health` endpoint for load-balancer/orchestrator probes, and a `setInterval`-based periodic self-report — are NOT enumerated in the O-series of this chapter because they are routing-layer and emission-cadence variants of the primitives above; they are tracked instead in [09-optimization-recommendations.md](./09-optimization-recommendations.md) as **A3-1** (`/health` route, ADVISORY-C001 + ADVISORY-C003) and **A1-6** (periodic self-report, ADVISORY-C001) respectively, and the Summary closing-paragraph below points reviewers at those entries when the routing-layer or continuous-cadence pattern is the right fit.

## O1. Structured Request Logging

- **Tag**: **ADVISORY-C001 + ADVISORY-C002**.
- **Proposal.** Add a structured-logger library to the application's dependency graph and use it to emit one log entry per inbound HTTP request. The canonical choice for a Node.js project of this shape is `pino` — a JSON-by-default logger with low per-call overhead and a stable single-package public API — but `bunyan`, `winston`, or any other structured logger would satisfy the recommendation equivalently. Concretely: add `"pino": "^9.0.0"` (or the current stable major) to the `dependencies` object inside `[package.json:L1-L11]`, run `npm install` to regenerate `[package-lock.json:L6-L11]`, and modify `[server.js]` to (a) require the logger at `[server.js:L1]` alongside the existing `const http = require('http');` — adding `const logger = require('pino')();` as a new line — and (b) emit one structured log entry per request inside the handler at `[server.js:L6-L10]`, ideally after `res.statusCode = 200` at `[server.js:L7]` and before `res.end('Hello, World!\n')` at `[server.js:L9]`, with a call such as `logger.info({ method: req.method, url: req.url, statusCode: 200 }, 'request')`. The handler does not need to change its response shape, its status code, its content-type, or its body; the logging call is purely additive and has no effect on the 14-byte response payload.
- **Dependency footprint.** One new direct dependency in `[package.json:L1-L11]`. Pino's transitive footprint is approximately six packages (the exact count can be confirmed with `npm ls pino` once installed); this includes Pino's own helper modules (`pino-std-serializers`, `quick-format-unescaped`, `atomic-sleep`, `on-exit-leak-free`, `safe-stable-stringify`, `thread-stream`) and the SonicBoom write-stream primitive. Relative to the current state at `[package-lock.json:L6-L11]` — an empty `packages` map under the root entry — this is a substantive change to the dependency posture and is what Constraint C-002 is written to prevent. The harness package under `benchmarks/` is **not** an alternative location for this dependency, because the logger must live inside the application's package graph to be reachable from `[server.js:L1]` via `require('pino')`; the harness's `node_modules` is on a separate resolution path and cannot satisfy a `require` from the parent `server.js` file.
- **Source-modification footprint.** Two lines added to `[server.js:L1-L14]`: one line at `[server.js:L1]` for the `require('pino')` import, and one line inside the handler at `[server.js:L6-L10]` for the `logger.info(...)` call. No existing line of `[server.js:L1-L14]` is deleted, reordered, or syntactically altered — the change is purely additive. The two added lines together expand the file from 14 lines to 16 lines, and the handler grows from 3 statements to 4 statements; the file remains short enough to read in one screen and the original structure is preserved.
- **Constraints relaxed.** Constraint C-001 per `[README.md:L2]` and `[Section 2.6.2]` — the source modification at `[server.js:L1]` and `[server.js:L6-L10]` — and Constraint C-002 per `[Section 2.6.2]` — the dependency addition to `[package.json:L1-L11]`. Both constraints must be relaxed by explicit owner approval before O1 can be applied; relaxing only one is insufficient (a dep-only relaxation produces an unused dependency, and a source-only relaxation cannot satisfy the `require('pino')` call). Constraint C-003 ("Single-purpose") is **not** implicated because no URL branching is introduced — every inbound request still goes through the same single response path, and the logger call simply records what flowed through it.
- **Operational benefit.** Every inbound request becomes attributable: an operator inspecting the captured log stream can grep entries by HTTP method, URL path, status code, and (with one additional `Date.now()` capture at the start of the handler and a subtraction at the end) per-request latency. This unlocks the standard set of forensic and diagnostic workflows that today are structurally impossible in this codebase — answering questions like "how many requests came in during the last five minutes?", "what URLs are clients actually requesting?", "is the request rate climbing or falling?", "are there clients sending malformed requests?", and "what was the latency distribution of the requests that completed in the window of interest?". The Pino default output is one line of JSON per log entry, suitable for ingestion into any log-aggregation pipeline (Loki, Elasticsearch, Splunk, Datadog Logs) without further transformation. The per-call overhead of `logger.info({...}, '...')` at Pino's JSON-default level is on the order of 5–15 microseconds on modern hardware — small relative to the ~50–200 microseconds the static-handler path itself consumes per request per [04-cpu-and-memory-profile.md](./04-cpu-and-memory-profile.md), but non-zero, so the recommendation does mildly degrade peak throughput in exchange for visibility. Reviewers approving the O1 lift should consult [05-latency-and-throughput.md](./05-latency-and-throughput.md) for the baseline numbers against which the post-O1 overhead can be compared once O1 is applied and re-measured.
- **Sensitive-data redaction caveat (REQUIRED before approval).** The proposal above logs `req.method`, `req.url`, and `res.statusCode` only. While the current handler at `[server.js:L6-L10]` ignores all request input per `[Section 5.1.3]` and the codebase therefore has no clients submitting credentials today, **any future relaxation of C-001/C-003 that introduces request-data reading would expose the log stream to PII and secret leakage**, and the C-002 relaxation that this recommendation already requires must be conditioned on explicit redaction guarantees in the log call. The following rules MUST be encoded in the log-call configuration before O1 is approved: (a) **never log the `Authorization` request header** under any circumstance — bearer tokens, basic-auth credentials, API keys, and HMAC signatures all flow through this header; (b) **never log the `Cookie` or `Set-Cookie` headers** because session identifiers, authentication state, and CSRF tokens routinely live in cookies; (c) **never log `Proxy-Authorization`** for the same reason as `Authorization`; (d) **redact query-string credentials** — strip any `req.url` query parameters whose key matches a case-insensitive deny-list of `token`, `access_token`, `api_key`, `apikey`, `secret`, `password`, `pwd`, `auth`, `key`, `signature`, `sig` before passing the URL to the logger; (e) **avoid request-body logging by default** — never include `req` body content in the log call without an explicit owner-approved schema that enumerates which body fields are safe to log and applies field-level masking to the rest; (f) **document any future header or body capture as opt-in with masking** in the log-call options, so that the default posture remains "log nothing sensitive" and any deviation is a visible owner-approved change. Pino supports redaction natively via its `redact: { paths: [...], censor: '[Redacted]' }` option; the operator implementing O1 SHOULD pass an explicit `redact` config rather than relying on the handler to filter the fields manually. Reviewers approving the O1 lift MUST treat the redaction configuration as a load-bearing precondition of approval, not as a follow-on detail.
- **Alternative READY-adjacent approach (documented for honesty; does NOT replace structured logging).** The harness scripts can capture the server's standard-output stream by invoking `node ../server.js | tee server.log` rather than `node ../server.js`; this redirects the startup line at `[server.js:L13]` and any future stdout output to a file. Because the server emits no per-request stdout output, this approach captures only the one startup line — it does not produce per-request logs and therefore does not unlock any of the forensic workflows enumerated above. The approach is mentioned here only for completeness so reviewers do not mistakenly treat it as an equivalent substitute; it is, narrowly, a harness-side stdout redirection that requires zero source modification and zero dependency addition, but it solves a different (and much smaller) problem than O1 does.
- **Cross-reference.** [09-optimization-recommendations.md](./09-optimization-recommendations.md), the ADVISORY-C001 + ADVISORY-C002 observability sub-section that aggregates O1 alongside O2 and O3.

## O2. Prometheus `/metrics` Exposition

- **Tag**: **ADVISORY-C001 + ADVISORY-C002 + ADVISORY-C003**.
- **Proposal.** Expose a Prometheus-style metrics endpoint at `GET /metrics` that emits per-process counters and histograms in the OpenMetrics text exposition format. Concretely: add `"prom-client": "^15.0.0"` (or the current stable major) to the `dependencies` object inside `[package.json:L1-L11]`, run `npm install` to regenerate `[package-lock.json:L6-L11]`, declare one or more metrics at module scope in `[server.js]` — at minimum a `Counter` named `http_requests_total` and ideally also a `Histogram` named `http_request_duration_seconds` — and modify the handler at `[server.js:L6-L10]` to branch on `req.url`: when the path is `/metrics`, the handler emits the prom-client registry contents with the OpenMetrics content-type; for all other paths, the handler increments the counter, records the histogram observation, and emits the existing `200 OK` static response. A representative diff for the handler is:

  ```js
  const client = require('prom-client');
  const httpRequestsTotal = new client.Counter({
    name: 'http_requests_total',
    help: 'Total HTTP requests',
    labelNames: ['method', 'status'],
  });

  const server = http.createServer(async (req, res) => {
    if (req.url === '/metrics') {
      res.setHeader('Content-Type', client.register.contentType);
      res.end(await client.register.metrics());
      return;
    }
    httpRequestsTotal.inc({ method: req.method, status: 200 });
    res.statusCode = 200;
    res.setHeader('Content-Type', 'text/plain');
    res.end('Hello, World!\n');
  });
  ```

  The handler now contains two distinct response paths and is no longer the single-branch static-handler that `[server.js:L6-L10]` is by Constraint C-003. The handler signature also acquires the `async` keyword because `client.register.metrics()` returns a Promise; an alternative implementation can avoid `async` by calling the synchronous `client.register.metrics()` overload available in prom-client v14.x and earlier, but the asynchronous form is recommended for newer prom-client versions.
- **Dependency footprint.** One new direct dependency in `[package.json:L1-L11]`. The `prom-client` library has historically had a small transitive footprint — typically one to three packages including `tdigest` for the histogram quantile computation and `bintrees` as its dependency — though the exact count varies by major version and can be verified with `npm ls prom-client` after install. Relative to the current zero-dep posture at `[package-lock.json:L6-L11]`, this remains a small footprint compared to OpenTelemetry (O3 below) but is still a meaningful departure from Constraint C-002.
- **Source-modification footprint.** Approximately ten lines added to `[server.js:L6-L10]` plus the metric declaration at module scope. The handler is no longer a single-purpose static-response branch — it routes on `req.url`, which is the structural change that Constraint C-003 ("Single-purpose") is written to prevent. Per `[Section 5.1.3]` ("no data from the incoming request — method, path, headers, or body — is read, evaluated, or stored"), the current handler intentionally treats every request identically; introducing the `/metrics` branch requires the handler to begin reading `req.url`, which violates that property. Reviewers should be aware that this is a more significant structural change than O1's purely additive logging.
- **Constraints relaxed.** Constraint C-001 per `[README.md:L2]` and `[Section 2.6.2]` (source modification at `[server.js:L6-L10]`), Constraint C-002 per `[Section 2.6.2]` (dependency addition to `[package.json:L1-L11]`), and Constraint C-003 per `[Section 2.6.2]` (introduction of URL branching in the handler). All three constraints must be relaxed; this is the highest constraint-relaxation cost in the chapter and the reason O2 is listed below O1 in the Summary table even though metrics offer arguably the richest operational value.
- **Operational benefit.** The `/metrics` endpoint enables scraping by Prometheus, Mimir, Cortex, VictoriaMetrics, or any other OpenMetrics-compatible time-series database, which in turn enables visualization in Grafana, alerting via Alertmanager, and quantitative analysis over arbitrary time windows. With the `http_requests_total` counter and the `http_request_duration_seconds` histogram emitted, the standard "RED method" operational dashboard (Rate, Errors, Duration) becomes achievable: request rate over any window, error rate (4xx/5xx as a fraction of total — currently always zero given the unconditional `200 OK` at `[server.js:L7]`), and latency distribution at any percentile. The prom-client library additionally provides the `collectDefaultMetrics()` helper, which automatically exposes the standard Node.js process metrics (heap, RSS, event-loop lag, GC pause durations) without further code; reviewers approving O2 should consider enabling `collectDefaultMetrics()` for the additional `process_*` and `nodejs_*` metric families it produces. The post-O2 numbers from [04-cpu-and-memory-profile.md](./04-cpu-and-memory-profile.md) and [05-latency-and-throughput.md](./05-latency-and-throughput.md) will differ from the pre-O2 baseline — the histogram observation is a small per-request overhead (single-digit microseconds at p50) — so the chapter recommends re-running the harness after O2 is applied to capture the post-O2 baseline.
- **Cross-reference.** [09-optimization-recommendations.md](./09-optimization-recommendations.md), the ADVISORY-C001 + ADVISORY-C002 + ADVISORY-C003 observability sub-section. O2 is the only recommendation in this chapter that carries all three constraint tags simultaneously.

## O3. OpenTelemetry Tracing

- **Tag**: **ADVISORY-C001 + ADVISORY-C002**.
- **Proposal.** Adopt the OpenTelemetry Node.js SDK with its auto-instrumentation bundle, configured to capture every inbound HTTP request as a span and emit those spans to a configured collector (OTLP HTTP/gRPC, Jaeger, Zipkin, or any OpenTelemetry-compatible backend). Concretely: add the three packages `"@opentelemetry/sdk-node"`, `"@opentelemetry/auto-instrumentations-node"`, and a chosen exporter such as `"@opentelemetry/exporter-trace-otlp-http"` (or `@opentelemetry/exporter-jaeger`, `@opentelemetry/exporter-zipkin`) to the `dependencies` object inside `[package.json:L1-L11]`, run `npm install` to regenerate `[package-lock.json:L6-L11]`, and initialize the SDK at the top of `[server.js]` — **before** the existing `const http = require('http');` at `[server.js:L1]`, because the auto-instrumentation has to register its hooks before the `http` module is loaded. A representative initialization stanza is:

  ```js
  const { NodeSDK } = require('@opentelemetry/sdk-node');
  const { getNodeAutoInstrumentations } = require('@opentelemetry/auto-instrumentations-node');
  new NodeSDK({ instrumentations: [getNodeAutoInstrumentations()] }).start();
  ```

  The handler at `[server.js:L6-L10]` is **not** modified — the auto-instrumentation registers a monkey-patch against the `http` module's request and response lifecycle at SDK startup, and every subsequent `http.createServer` call automatically produces a span around each inbound request without any handler-level code change. This is the structural reason O3 does not violate Constraint C-003: no URL branching is introduced, no alternate response paths exist, and the handler remains the single-purpose static responder it is today.
- **Dependency footprint.** Three or more direct dependencies in `[package.json:L1-L11]` (the SDK, the auto-instrumentation bundle, and at least one exporter), plus a substantial transitive footprint. OpenTelemetry's modular architecture means that `@opentelemetry/auto-instrumentations-node` alone pulls in dozens of `@opentelemetry/instrumentation-*` packages — one per instrumented Node.js module (`http`, `https`, `dns`, `fs`, `net`, `redis`, `pg`, `mysql`, and many others). The post-install package count is typically 30+ packages, possibly more depending on the chosen exporter and on transitive bumps. This is a substantial departure from the current zero-dep state recorded at `[package-lock.json:L6-L11]`, far larger than the footprints of O1 (~6 packages) and O2 (~1–3 packages); reviewers approving O3 should be prepared for a `node_modules` directory of several tens of megabytes where today there is none.
- **Source-modification footprint.** Approximately five lines added at the **top** of `[server.js]`, before the existing line 1. The handler itself at `[server.js:L6-L10]` does **not** need modification because auto-instrumentations hook the `http` module at load time. The handler's body remains the three statements at `[server.js:L7-L9]`, exactly as today, and continues to read no request data per `[Section 5.1.3]`. The structural shape of the file is preserved; only the prologue grows.
- **Constraints relaxed.** Constraint C-001 per `[README.md:L2]` and `[Section 2.6.2]` (source modification at the top of `[server.js]`) and Constraint C-002 per `[Section 2.6.2]` (three+ dependency additions to `[package.json:L1-L11]`). Constraint C-003 ("Single-purpose") is **not** violated — no new route is introduced, no URL branching is added, and no handler-level logic change occurs. This is what distinguishes O3 from O2 in the tag inventory: O3 has the larger dependency footprint but the smaller routing footprint.
- **Operational benefit.** Each inbound request is wrapped in a span that captures the HTTP method, URL, status code, response size, and duration with sub-millisecond precision; the span is automatically tagged with the OpenTelemetry semantic conventions (`http.method`, `http.target`, `http.status_code`, `net.host.name`, etc.), making the trace data interoperable with any OpenTelemetry-compatible analysis backend. If and when the application is composed with other services — currently no downstream calls exist per `[Section 3.4.1]` and `[Section 5.1.4]`, so this future-tense composition is hypothetical — the SDK additionally propagates trace context (via the W3C `traceparent` header by default) so that distributed traces can be assembled across the service graph. **For the current single-service shape of `[server.js:L1-L14]`, the practical value of O3 is limited to ingress visibility** — the same per-request data that O1 captures as JSON log lines is captured as OpenTelemetry spans, but with structured fields, native percentile aggregation in the backend, and built-in semantic conventions. Reviewers comparing O1 and O3 head-to-head should consider that O1 delivers most of the per-request observability value for a tenth of the dependency footprint; O3's marginal value over O1 is realized primarily when the application is extended with downstream calls, which is not in scope for the current codebase per Constraints C-001 and C-003.
- **Security caveat — OpenTelemetry package vulnerabilities (REQUIRED before approval).** OpenTelemetry SDK, auto-instrumentation, and Prometheus-exporter package paths have historically had advisories on the OSV/GHSA databases — including (but not limited to) GHSA-q7rr-3cgh-j5r3 / CVE-2026-44902 covering exporter and SDK package paths — and reviewers approving the O3 lift MUST verify that the specific `@opentelemetry/*` versions selected at install time are at or above the patched line published in the relevant advisory (for the cited GHSA-q7rr-3cgh-j5r3 / CVE-2026-44902, that floor is `>=0.217.0` on the patched package paths; reviewers must confirm the current advisory line because vulnerability data evolves between this document's authoring and its application). The verification procedure before lifting C-002 for any `@opentelemetry/*` addition is: (a) run `npm audit --omit=optional --json` after the dependency is installed in a scratch directory and fail-stop the approval if any HIGH or CRITICAL advisory is reported against any `@opentelemetry/*` path; (b) cross-check against `https://osv.dev` for each `@opentelemetry/*` package name and major version selected; (c) record the resolved version of each `@opentelemetry/*` package in the change-approval record so that any future re-audit can verify the version has not been silently downgraded; (d) prefer the most recent patched minor of each major over pinning to an old known-vulnerable minor. Until these steps are recorded against a specific commit, the O3 recommendation is NOT approvable — vulnerability verification is a load-bearing precondition, not a follow-on detail.
- **Sensitive-data redaction caveat (REQUIRED before approval).** The auto-instrumentations bundle captures the HTTP method, URL (including any query string), status code, response size, and standard request/response headers as span attributes via the OpenTelemetry HTTP semantic conventions. While the current handler ignores all request input per `[Section 5.1.3]`, **any future relaxation that introduces request-data reading or the addition of clients submitting credentials would surface PII and secrets in span attributes**, and the C-002 relaxation this recommendation requires must therefore be conditioned on explicit redaction guarantees in the OpenTelemetry SDK configuration. The following rules MUST be encoded before O3 is approved: (a) configure `@opentelemetry/instrumentation-http` with `headersToSpanAttributes: { server: { ... } }` set to an explicit allow-list — never the default which captures all headers — and ensure `Authorization`, `Cookie`, `Set-Cookie`, and `Proxy-Authorization` are NOT included in the allow-list under any circumstance; (b) configure the SDK with a `SpanProcessor`-level filter that strips query-string credentials from the `http.target` attribute using the same case-insensitive deny-list as O1 above (`token`, `access_token`, `api_key`, `apikey`, `secret`, `password`, `pwd`, `auth`, `key`, `signature`, `sig`); (c) disable request-body / response-body capture by ensuring `requestHook`/`responseHook` callbacks do not write `req.body` or response payloads onto span attributes — these hooks default to disabled in the auto-instrumentation, but explicit confirmation that they remain disabled is required; (d) configure the OTLP exporter endpoint over TLS in any deployment, because the exporter forwards span attributes (potentially including the partially-redacted URL above) over the wire to a downstream collector and the channel must be confidentiality-protected. Reviewers approving the O3 lift MUST treat both this redaction configuration AND the vulnerability verification above as load-bearing preconditions of approval, not as follow-on detail.
- **Cross-reference.** [09-optimization-recommendations.md](./09-optimization-recommendations.md), the ADVISORY-C001 + ADVISORY-C002 observability sub-section. Note that O1 and O3 share the same tag pair (C-001 + C-002) but differ markedly in dependency and source-modification footprint — the Summary table at the end of this chapter highlights the difference for direct comparison.

## O4. APM Integration

- **Tag**: **ADVISORY-C001 + ADVISORY-C002**.
- **Proposal.** Adopt a commercial Application Performance Monitoring (APM) agent that auto-instruments the Node.js runtime and the `http` module, captures per-request transactions, samples CPU/memory/event-loop metrics, and forwards the resulting telemetry to a hosted APM backend for storage, query, and alerting. The canonical choices for a Node.js HTTP application of this shape are `newrelic` (New Relic Node Agent), `dd-trace` (Datadog APM), and `elastic-apm-node` (Elastic APM Agent); the analysis below uses `newrelic` as the representative example because it is the most widely deployed and has the most mature documentation, but the proposal is agent-agnostic in shape. Concretely: add `"newrelic": "^11.0.0"` (or the current stable major of the chosen agent) to the `dependencies` object inside `[package.json:L1-L11]`, run `npm install` to regenerate `[package-lock.json:L6-L11]`, place a `newrelic.js` configuration file at the application root specifying the license key and application name (or supply equivalent values via the agent's environment-variable interface), and `require('newrelic')` as the **very first statement** of `[server.js]` — before the existing `const http = require('http');` at `[server.js:L1]`, because most APM agents must register their instrumentation hooks before the `http` module is loaded. A representative initialization is:

  ```js
  require('newrelic');
  const http = require('http');
  // ... existing [server.js:L3-L14] body unchanged
  ```

  The handler at `[server.js:L6-L10]` is **not** modified — the APM agent registers a monkey-patch against the `http` module's request/response lifecycle at agent startup, and every subsequent `http.createServer` call is automatically observed without any handler-level code change. APM agents differ in detail (Datadog's `dd-trace` requires `dd-trace.init()` instead of a bare `require`; Elastic's `elastic-apm-node` requires `require('elastic-apm-node').start({ ... })`), but the structural pattern is identical: a one-line pre-`http` require that hooks the runtime.
- **Dependency footprint.** Substantial. APM agents typically pull 30–80 transitive packages — the agent itself, its instrumentation bundles per Node.js module, its serialization layer for the backend protocol, its sampling/rate-limiting primitives, and (in some agents) a native add-on for V8-internal hooks. The post-install `node_modules` directory is typically a few tens of megabytes where today there is none. This dependency footprint is comparable to O3's (OpenTelemetry) in magnitude and is therefore subject to the same vulnerability-verification discipline (see security caveat below).
- **Source-modification footprint.** Approximately one to five lines added at the **very top** of `[server.js]`, before the existing line 1. The handler itself at `[server.js:L6-L10]` is not modified — auto-instrumentation hooks the `http` module at load time. The agent's configuration file (`newrelic.js` or equivalent) is a separate file at the application root, not a `[server.js]` edit, and its existence is itself a source-tree change requiring C-001 relaxation. The structural shape of `[server.js]` is preserved; only the prologue grows.
- **Constraints relaxed.** Constraint C-001 per `[README.md:L2]` and `[Section 2.6.2]` (modification of the top of `[server.js]` plus the addition of the agent's configuration file at the application root) and Constraint C-002 per `[Section 2.6.2]` (substantial dependency addition to `[package.json:L1-L11]`). Constraint C-003 is **not** implicated because no new route is introduced and no URL branching is added; Constraint C-004 is **not** implicated because the agent's runtime configuration is supplied via its dedicated config file (which the C-001 relaxation already covers) rather than via `process.env.PORT`/`process.env.HOST` reads inside `[server.js]`. **O4 is the smallest dependency-footprint commercial-APM recommendation in this chapter**; the choice between O3 (OpenTelemetry, vendor-neutral, self-hosted backend possible) and O4 (commercial APM, vendor-locked, hosted backend) is an architectural decision that this chapter does not adjudicate — both are tagged at the same constraint-relaxation cost and reviewers select based on operational preference and contractual relationship with the APM vendor.
- **Operational benefit.** A commercial APM integration delivers, out of the box, a far broader observability surface than any individual O1/O2/O3 layer above: **transactions** (per-request traces with timing breakdowns for parser, handler, and write phases — analogous to O3's spans but enriched with backend-side analysis and visualization); **errors** (any uncaught exception or rejected promise is captured with stack trace and rate-of-occurrence — relevant if Constraint C-001 is also lifted to enable error handlers in `[server.js]`); **infrastructure metrics** (CPU%, RSS, heap, event-loop lag, GC pause histograms — analogous to O2's prom-client metrics but emitted to the APM backend without operator scraping); **synthetic checks** (most APM vendors layer external uptime probes on top of the agent telemetry, providing an external corroborating signal for the in-process telemetry); and **dashboards and alerts** out of the box, requiring no Grafana/Alertmanager/PagerDuty wiring (those integrations are pre-built in the APM vendor's UI). The trade-off is **vendor lock-in** — moving from one APM vendor to another typically requires changing both the dependency and the agent-initialization stanza in `[server.js]`, and the captured historical data lives in the vendor's backend with limited export options. Reviewers comparing O3 (vendor-neutral OpenTelemetry) and O4 (vendor-locked APM) head-to-head should weigh: (a) the operational benefit of APM's pre-built dashboards/alerts/SLOs against the architectural benefit of OpenTelemetry's vendor portability; (b) the dependency-footprint parity (both pull 30–80 transitive packages); (c) the contractual cost — commercial APM is a recurring license fee, while OpenTelemetry is open-source plus a self-hosted backend (Jaeger, Tempo, Grafana Loki) or a backend-as-a-service. The right answer is organization-specific, not codebase-specific.
- **Security caveat — APM agent vulnerabilities (REQUIRED before approval).** Commercial APM agents have historically had CVEs disclosed against their wire protocols, configuration parsers, and instrumentation paths. Before lifting C-002 for any APM agent, reviewers MUST: (a) run `npm audit --omit=optional --json` against a scratch install of the chosen agent and fail-stop on any HIGH or CRITICAL advisory; (b) cross-check the agent's name and major version against `https://osv.dev` and the vendor's published security advisories page; (c) record the resolved version in the change-approval record; (d) prefer the most recent patched minor over an older minor. The same discipline applies as for O3's `@opentelemetry/*` packages — vulnerability verification is a load-bearing precondition of approval. The license-key transmission channel is also security-sensitive: APM agents typically embed the license key in plaintext in `newrelic.js` or in the equivalent environment variable, and that file MUST NOT be committed to version control under any circumstance — `.gitignore` entries for `newrelic.js` / `dd-trace.config.js` / equivalent MUST be in place before any commit, and reviewers MUST verify the license-key file is excluded by `git check-ignore newrelic.js` before approval.
- **Sensitive-data redaction caveat (REQUIRED before approval).** APM agents capture per-request transactions that may, by default, include request URLs (with query strings), request headers, and (in some configurations) request bodies. While the current handler ignores all request input per `[Section 5.1.3]`, **any future relaxation that introduces request-data reading would expose the captured transactions to PII and secret leakage**, and the C-002 relaxation this recommendation requires must therefore be conditioned on explicit redaction guarantees in the agent's configuration. The following rules MUST be encoded in the chosen agent's configuration before O4 is approved: (a) **enable URL-query redaction** — every major APM agent supports an "attribute include/exclude" list; ensure the case-insensitive deny-list of `token`, `access_token`, `api_key`, `apikey`, `secret`, `password`, `pwd`, `auth`, `key`, `signature`, `sig` is applied to URL query parameters before they are recorded; (b) **disable request-header capture by default** — explicitly disable `Authorization`, `Cookie`, `Set-Cookie`, and `Proxy-Authorization` capture; in New Relic's `newrelic.js` config this is `attributes.exclude: ['request.headers.authorization', 'request.headers.cookie', 'request.headers.set-cookie', 'request.headers.proxy-authorization']`; in `dd-trace` it is `DD_TRACE_HTTP_RECORD_HEADERS=false` or the equivalent allow-list; (c) **disable request-body capture by default** — most agents disable this by default but explicit confirmation is required; (d) **enforce TLS on the agent-to-backend channel** — every modern APM agent uses TLS by default for its egress, but in air-gapped or proxied deployments the operator must confirm the agent is not falling back to plaintext. Reviewers approving the O4 lift MUST treat both the vulnerability verification above AND this redaction configuration as load-bearing preconditions of approval.
- **Cross-reference.** [09-optimization-recommendations.md](./09-optimization-recommendations.md), the ADVISORY-C001 + ADVISORY-C002 observability sub-section. O4 is the commercial-APM counterpart to O3's vendor-neutral OpenTelemetry; the two recommendations carry identical tag pairs (C-001 + C-002) and identical-magnitude dependency footprints, and reviewers select based on operational preferences rather than technical constraints. The chapter does not promote a `/health` endpoint as an O-numbered observability primitive because health-probe routing is already covered by chapter 09's recommendation A3-1 (ADVISORY-C001 + ADVISORY-C003) as a routing-layer concern rather than an observability layer concern; reviewers who specifically want a distinguishable `GET /health` response should consult A3-1 in chapter 09 directly.

## O5. Process-Level External Observation

- **Tag**: **ADVISORY-C001** (single-constraint, smallest footprint).
- **Proposal.** At module scope in `[server.js]`, register a signal handler that emits a single JSON line of process-level resource state to standard output when the operator delivers the agreed-upon signal (`SIGUSR2`, which is reserved for application use on POSIX systems and is not consumed by Node.js's own `--inspect` handling — that mechanism uses `SIGUSR1`). The signal handler reads `process.memoryUsage()` (RSS, heap-used, heap-total, external, array-buffers) and `process.cpuUsage()` (user and system CPU time since process start) and writes a one-line JSON snapshot to stdout; an external operator triggers the snapshot on demand via `kill -USR2 <pid>` from any shell on the same host. The pattern is "process-level external observation" in the precise sense that **the observation is initiated externally** (by the operator's `kill` command) and **observes process-level resource state** (RSS, heap, CPU) rather than per-request behavior. A representative implementation is:

  ```js
  process.on('SIGUSR2', () => {
    const m = process.memoryUsage();
    const c = process.cpuUsage();
    console.log(JSON.stringify({
      ts: Date.now(), event: 'sigusr2',
      rss: m.rss, heapUsed: m.heapUsed, heapTotal: m.heapTotal, external: m.external,
      cpuUser: c.user, cpuSystem: c.system,
    }));
  });
  ```

  The handler is purely event-driven — it consumes no resources between signals (there is no recurring timer to keep the event loop awake, in contrast to a `setInterval` self-report pattern) and produces no output until an operator explicitly requests it. This makes the observation footprint **strictly zero at rest**: the running process is byte-for-byte indistinguishable from the pre-O5 process in terms of stdout volume, event-loop activity, and any quantitative metric, until the operator delivers SIGUSR2. The emission target is the same standard-output file descriptor that `[server.js:L13]` already writes to, so the snapshot interleaves with the existing startup line without requiring any new output destination, log-rotation policy, or formatter configuration.
- **Dependency footprint.** Zero. Every primitive used — `process.on`, `process.memoryUsage()`, `process.cpuUsage()`, `Date.now()`, `console.log`, `JSON.stringify` — is a Node.js built-in already available at runtime without any `require`. Constraint C-002 ("Zero external dependencies") is **not** implicated. The choice of `SIGUSR2` over `SIGUSR1` is deliberate: `SIGUSR1` triggers the V8 inspector listener in Node.js by default and is therefore not safe to repurpose for application logic without unintentionally suppressing the standard `--inspect` workflow; `SIGUSR2` is reserved for application-defined behaviour on POSIX and does not conflict with any Node.js built-in signal handling. Operators on Windows MUST be aware that POSIX signals are not first-class on Windows; the recommendation is POSIX-only and an equivalent on Windows would require a different trigger mechanism (e.g., a named pipe or a Windows-specific event), which is out of scope for the typical Linux/macOS deployment substrate of this codebase.
- **Source-modification footprint.** Approximately five lines added at module scope in `[server.js]` — the `process.on('SIGUSR2', ...)` registration plus the callback body. The handler at `[server.js:L6-L10]` is **not** modified. The change is purely additive at module scope and does not alter the handler's response shape, the listening socket, the startup log, or any other observable property of the current behaviour at rest. The line count of `[server.js]` grows from 14 to approximately 19; the structural shape is preserved.
- **Constraints relaxed.** Constraint C-001 per `[README.md:L2]` and `[Section 2.6.2]` only. No dependency is added (C-002 untouched), no URL branching is introduced (C-003 untouched — the handler at `[server.js:L6-L10]` is not modified and continues to respond to every URL with the same static response), and no configuration is parameterized (C-004 untouched — the signal name is hard-coded). **O5 is the smallest constraint-relaxation footprint in this chapter** — exactly one constraint (C-001) must be lifted, by exactly one decision (approval of an ~5-line source modification), with no transitive cost.
- **Operational benefit.** An operator who wants a point-in-time snapshot of process-level resource state — for instance, when investigating a suspected memory leak or a CPU spike reported by an external monitor — delivers `kill -USR2 <pid>` from any shell on the same host and reads the resulting JSON line from the server's captured stdout (visible in the foreground terminal in the canonical `node server.js` workflow per `[Section 1.3.1]`, or in the supervisor/systemd journal in a daemonized deployment). The on-demand nature is the key distinction from a `setInterval`-based self-report: **zero output is produced when no operator is investigating**, which keeps stdout uncluttered and preserves the existing startup-only emission pattern at `[server.js:L13]` during normal operation. The operational ceiling of O5 is single-point-in-time snapshots — it does not provide a continuous time-series, does not survive across process restarts (no historical data is retained), and does not propagate beyond the host (no remote scraping). For continuous time-series or remote scraping, reviewers should consider O2 (Prometheus `/metrics` exposition) or O4 (commercial APM) — both substantially richer at substantially higher constraint-relaxation cost. **O5 is the lowest-footprint observability change in this chapter** and is the recommended entry point for an organization that wants some inside-the-process visibility but is unwilling to lift more than one constraint.
- **Sensitive-data redaction caveat.** O5 emits only process-level resource state (RSS, heap, CPU) — it does **not** capture request URLs, request headers, request bodies, or any other request-scoped data. The PII and secret leakage concerns that apply to O1/O3/O4 are therefore structurally not implicated by O5. Reviewers should nonetheless treat the snapshot stream as host-confidential — RSS and heap deltas can carry side-channel information about workload patterns under a sufficiently sophisticated adversary — and ensure that the standard-output destination is access-controlled in any deployment (the file descriptor inherited by the supervisor or the journal entry of the systemd unit MUST be readable only by accounts authorized to operate the application).
- **Cross-reference.** [09-optimization-recommendations.md](./09-optimization-recommendations.md), the ADVISORY-C001 observability sub-section. O5 is the only recommendation in this chapter that carries a single-constraint tag; every other entry requires at least two constraints to be lifted simultaneously. The chapter does not promote a `setInterval`-based periodic self-report as an O-numbered observability primitive because it is already covered by chapter 09's recommendation A1-6 (ADVISORY-C001) as the periodic-emission counterpart to O5's on-demand-emission pattern; reviewers who specifically want continuous self-reporting rather than on-demand snapshots should consult A1-6 in chapter 09 directly.

## Summary

The five recommendations differ in three axes — the set of constraints each requires to be lifted, the number of new dependencies each adds to `[package.json:L1-L11]`, and the number of source lines each adds to `[server.js:L1-L14]`. The table below is the canonical side-by-side comparison; rows are ordered by ascending constraint-relaxation footprint (O5 lifts one constraint with the smallest footprint; O1, O3, and O4 lift two with progressively larger dependency footprints; O2 lifts three).

| ID | Recommendation | Tag(s) | Deps added | Source lines added | C-001? | C-002? | C-003? |
|----|----------------|--------|------------|--------------------|--------|--------|--------|
| O5 | Process-level external observation (SIGUSR2 on-demand snapshot) | ADVISORY-C001 | 0 | ~5 | ✓ | — | — |
| O1 | Structured request logging (Pino) | ADVISORY-C001 + ADVISORY-C002 | 1 (`pino`) | ~2 | ✓ | ✓ | — |
| O3 | OpenTelemetry tracing | ADVISORY-C001 + ADVISORY-C002 | 3+ (`@opentelemetry/*`) | ~5 | ✓ | ✓ | — |
| O4 | APM integration (New Relic / Datadog / Elastic) | ADVISORY-C001 + ADVISORY-C002 | 1 commercial agent (~30–80 transitive) | ~1–5 | ✓ | ✓ | — |
| O2 | Prometheus `/metrics` exposition | ADVISORY-C001 + ADVISORY-C002 + ADVISORY-C003 | 1 (`prom-client`) | ~10 | ✓ | ✓ | ✓ |

A "✓" in the C-001, C-002, or C-003 column indicates the recommendation requires the corresponding constraint per `[Section 2.6.2]` to be relaxed before it can be applied; a "—" indicates the constraint is **not** implicated by that recommendation and can remain in force. Note that Constraint C-004 ("Hardcoded configuration") is not implicated by any recommendation in this chapter — none of O1 through O5 introduces an environment-variable read, a config-file load, or a command-line argument; the recommendations are all source modifications and dependency additions, not parameterizations. The dependency-footprint column ranks O5 (zero deps) < O1 (one direct, ~6 transitive) < O2 (one direct, ~1–3 transitive) < O3 (three+ direct, ~30+ transitive) < O4 (one commercial agent, ~30–80 transitive) — and reviewers selecting between O3 and O4 should consult the "Operational benefit" sub-section of each entry because the choice is architectural (vendor-neutral OpenTelemetry vs. vendor-locked commercial APM) rather than technical.

All five recommendations are cross-referenced in [09-optimization-recommendations.md](./09-optimization-recommendations.md) under their respective constraint-tag sub-sections — O1, O3, and O4 under "ADVISORY-C001 + ADVISORY-C002", O2 under "ADVISORY-C001 + ADVISORY-C002 + ADVISORY-C003", and O5 under "ADVISORY-C001 (single-constraint)" — and every recommendation in this chapter is **ADVISORY**; **none is tagged READY**, consistent with the chapter's design and with AAP §0.8.1 ("Tagged recommendations"). Two related recommendations are tracked separately in chapter 09 rather than in this chapter's O-series because they are routing-layer or emission-cadence variants rather than observability primitives: **A3-1** (the `GET /health` endpoint, ADVISORY-C001 + ADVISORY-C003) covers the load-balancer/orchestrator health-probe pattern that an older draft of this chapter had labeled O4; **A1-6** (the periodic `setInterval` self-report, ADVISORY-C001) covers the continuous-cadence counterpart to O5's on-demand SIGUSR2 emission. Reviewers who want the health-probe pattern should consult A3-1; reviewers who want continuous self-reporting (as opposed to operator-triggered snapshots) should consult A1-6. Both are accessible from chapter 09 without re-traversing this chapter, and neither carries an additional security or redaction caveat beyond the ones recorded in their chapter-09 entries.

In addition to the constraint-relaxation requirements above, **two recommendations carry mandatory security preconditions that MUST be satisfied before approval** — these are not follow-on details but load-bearing gates: (a) O3 (OpenTelemetry) and O4 (commercial APM) both require explicit vulnerability verification of the chosen packages via `npm audit` and `osv.dev` cross-check, with the resolved versions recorded in the change-approval record; and (b) O1 (Pino), O3 (OpenTelemetry), and O4 (commercial APM) all require explicit sensitive-data redaction configuration covering `Authorization`/`Cookie`/`Proxy-Authorization` headers, query-string credentials, and request bodies — with header-allow-list/exclude-list configuration encoded in the chosen library's configuration interface rather than left to the handler-level filtering. Reviewers selecting which recommendations to apply should consult the constraint-relaxation policy in the broader repository governance documented at `[README.md:L2]` before lifting any of C-001 through C-003, AND ensure both security gates above are satisfied in the change-approval record before signing off on O1/O3/O4.
